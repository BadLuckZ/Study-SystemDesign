ความต่างอยู่ที่คำถามเดียว คือ 

> **ผู้ส่งต้องหยุดรอให้ได้ผลลัพธ์ก่อน จึงจะทำงานต่อมั้ย?**

---

## 1. Synchronous

การสื่อสารแบบ Synchronous คือการสื่อสารที่จะต้องรอให้ได้รับ Response มาก่อน จึงจะสามารถส่ง Request ถัดๆ ไปได้ มีลำดับการทำงานที่ชัดเจน

รูปแบบที่เจอบ่อยที่สุดคือ HTTP ผ่านการที่ Service A ยิง Request ไป Service B แล้วหยุดรอจนได้ Response กลับมา Service A จึงจะยิง Request ใหม่ไปหา Service B ได้ 

ข้อดีคือเข้าใจง่าย และตรงไปตรงมา implement ผ่านการเขียน function ทั่วๆ ไป แต่ข้อเสียก็มี เช่น
- **Performance ต่ำ** เพราะเกิด chain ของการรอ ถ้า A เรียก B, B เรียก C, C เรียก D แล้ว D ช้าแค่ตัวเดียว ทุกตัวที่รอต่อกันจะช้าตามหมดทั้งสาย
- **Failure Isolation แย่** ถ้า Service ปลายทางล่ม Service ต้นทางก็ไม่ได้ Response ค้างรอจน timeout กระทบเป็นลูกโซ่
- **Scale ยาก** เพราะไม่มีตัวกันชน ถ้า Traffic พุ่งขึ้นกะทันหัน Request จะทะลักเข้าไปที่ Service ปลายทางตรงๆ ทันที

โดยรวม Synchronous เหมาะกับระบบเล็กๆ ที่คนใช้ไม่เยอะ และงานที่จำเป็นต้องได้คำตอบทันทีจริงๆ ถึงจะทำต่อได้

---

## 2. Asynchronous

การสื่อสารแบบ Asynchronous คือการที่ผู้ส่ง**ไม่ต้องรอผลลัพธ์** ส่งงานออกไปแล้วทำงานต่อได้ทันที ทำได้ด้วยการใส่ตัวกลางคั่นไว้ (มักเป็น Queue) โดย Service A ส่งงานเข้า Queue แล้วไปทำอย่างอื่นต่อ ส่วน Service B ค่อยมาดึงงานไปทำเมื่อพร้อม

ผลที่ได้กลับด้านกับ Synchronous เกือบทุกข้อ

- **Performance ดีขึ้น** เพราะไม่มีใครต้องหยุดนั่งรอใคร ต่างคนต่างทำงานของตัวเองไป
- **Failure Isolation ดี** ถ้า Service B ล่ม งานก็ยังค้างรออยู่ใน Queue รอ B ฟื้นแล้วค่อยมาดึงไปทำ ไม่กระทบ A
- **Scale ง่าย** เพราะ Queue เป็นตัวกันชนรับ Traffic ที่พุ่งขึ้นกะทันหันไว้ให้ แล้วปล่อยให้ Service ปลายทางค่อยๆ ทยอยดึงไปทำตามกำลังที่ไหว

แต่ก็แลกมาด้วยความซับซ้อนที่เพิ่มขึ้น และผลลัพธ์ที่ไม่ได้เสร็จทันที (Eventual Consistency) ทำให้ต้องออกแบบเผื่อกรณีที่งานยังไม่เสร็จด้วย

โดย Asynchronous ยังแบ่งได้เป็น 2 แบบ ตามว่า message หนึ่งชิ้นถูกใครดึงไปใช้บ้าง

1. **Single Receiver**: message หนึ่งชิ้นถูกประมวลผลโดย Consumer เพียงตัวเดียว พอถูกดึงไปแล้วก็หายจาก Queue เลย ต่อให้มี Consumer หลายตัวรออยู่ message หนึ่งชิ้นก็ไปหาแค่ตัวใดตัวหนึ่ง เหมาะกับงานที่ต้องทำแค่ครั้งเดียว

2. **Multiple Receiver**: message หนึ่งชิ้นถูกดึงไปอ่านได้โดย Consumer **หลายตัว** และไม่หายไปหลังถูกอ่าน (เครื่องมือที่นิยมคือ Kafka) เหมาะกับกรณีที่ event เดียวต้อง trigger หลายอย่างพร้อมกัน เช่น event เดียวถูกส่งให้ทั้งระบบแจ้งเตือน ระบบเก็บสถิติ และระบบอื่นๆ อ่านพร้อมกันได้โดยไม่แย่งกัน
