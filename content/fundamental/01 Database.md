Database คือที่เก็บข้อมูล แบ่งเป็น 2 ประเภทหลักคือ **Relational Database (SQL)** และ **Non-Relational Database (NoSQL)** ต่างกันที่โครงสร้างข้อมูล วิธีดึงข้อมูล และ scaling

---

## 1. Relational Database (SQL)

โครงสร้างข้อมูลเป็น **Table** ที่ชัดเจน ตายตัว (fixed schema) แต่ละ table เชื่อมโยงกันผ่าน **Primary Key (PK)** และ **Foreign Key (FK)**

- ทุก row ใน table เดียวกัน ต้องมี field ครบตามที่กำหนดไว้ (schema เดียวกัน)
- การดึงข้อมูลข้าม table ต้องใช้ `JOIN`
- ACID Properties
- เหมาะกับข้อมูลที่มีความสัมพันธ์ซับซ้อน และต้องการความถูกต้องสูง

### ACID Properties

คุณสมบัติที่การันตีว่า Transaction จะทำงานถูกต้องและน่าเชื่อถือ

|Property|ความหมาย|กลไกที่ใช้|
|---|---|---|
|**Atomicity**|ถ้ามี action ย่อยใน transaction ทำไม่สำเร็จ ระบบจะ**ย้อนกลับทั้งหมด** (all or nothing)|Rollback|
|**Consistency**|ระบบจะ**ปฏิเสธ**การเปลี่ยนแปลงที่ทำให้ข้อมูลผิดเงื่อนไข (constraint) ที่กำหนดไว้|Constraint|
|**Isolation**|Transaction ที่ทำงานพร้อมกันจะไม่รบกวนกัน เหมือนถูกจัดคิวให้มีลำดับก่อน-หลัง|Multi-Version Concurrency Control (MVCC)|
|**Durability**|เมื่อ transaction สำเร็จแล้ว ผลลัพธ์จะ**คงอยู่ถาวร** แม้ระบบ crash|Transaction Log (WAL)|

> [!tip] จำง่ายๆ **A**tomicity = ทำให้ครบหรือไม่ทำเลย **C**onsistency = ข้อมูลต้องถูกกฎเสมอ **I**solation = ทำพร้อมกันแต่ไม่ชนกัน **D**urability = สำเร็จแล้วหายไม่ได้

### ตัวอย่าง

- **PostgreSQL** เป็น standard ของวงการ ใช้ได้กับแทบทุกระบบ, feature เยอะ, community ใหญ่

## 2. Non-Relational Database (NoSQL)

โครงสร้างข้อมูล**ยืดหยุ่น** (schema-less หรือ flexible schema)

- ใน table/collection เดียวกัน แต่ละ row/document ไม่จำเป็นต้องมี field เหมือนกัน (row A อาจขาด field ที่ row B มี)
- **ไม่ join** ข้ามตาราง แต่ละ row เก็บข้อมูลเป็น object สมบูรณ์ในตัวเอง (denormalized) → ดึงข้อมูลได้เร็วเพราะไม่ต้องรวมหลาย table
- รองรับ **Horizontal Scaling** ได้ดี คือเพิ่มจำนวน server (เครื่องราคาถูกได้) แทนที่จะอัปเกรดเครื่องเดิมให้แรงขึ้น (Vertical Scaling)
- **Partitioning/Sharding**: แบ่งข้อมูลกระจายไปหลาย node, บาง node เป็น storage หลัก บาง node เป็น replica (สำเนา) → เพิ่ม **Fault Tolerance** ถ้า node หลักล่ม ระบบยังใช้ข้อมูลจาก replica ต่อได้

### ประเภทย่อยของ NoSQL

| ประเภท            | ตัวอย่าง  | ลักษณะการเก็บข้อมูล                                                             |
| ----------------- | --------- | ------------------------------------------------------------------------------- |
| **Key-Value**     | Redis     | เก็บเป็นคู่ key-value เร็วมาก มักใช้เป็น cache                                  |
| **Document**      | MongoDB   | เก็บเป็น document (คล้าย JSON) ยืดหยุ่นสูง                                      |
| **Column-family** | Cassandra | เก็บเป็นคอลัมน์ เหมาะกับข้อมูลมหาศาล                                            |
| **Graph**         | Neo4j     | เก็บข้อมูลแบบ node-edge เหมาะกับข้อมูลที่เน้นความสัมพันธ์ (เช่น social network) |

## 3. เปรียบเทียบภาพรวม

| หัวข้อ               | Relational (SQL)                   | Non-Relational (NoSQL)                          |
| -------------------- | ---------------------------------- | ----------------------------------------------- |
| Schema               | ตายตัว ชัดเจน                      | ยืดหยุ่น                                        |
| ความสัมพันธ์ข้อมูล   | ใช้ JOIN                           | ไม่ join, เก็บเป็น object เดี่ยว                |
| ความถูกต้องของข้อมูล | สูง (ACID)                         | ยอมแลกความถูกต้องแบบเป๊ะ เพื่อความเร็ว/ยืดหยุ่น |
| การ Scale            | Vertical (อัปเกรดเครื่อง) เป็นหลัก | Horizontal (เพิ่มเครื่อง) ได้ดี                 |
| ความเร็วในการอ่าน    | ช้ากว่าเมื่อ join เยอะ             | เร็ว เพราะข้อมูลอยู่ในก้อนเดียว                 |
| ตัวอย่าง             | PostgreSQL, MySQL                  | MongoDB, Redis, Cassandra                       |

## 4. CAP Theorem

> [!info] CAP Theorem คือทฤษฎีที่อธิบายว่า **ทำไม NoSQL ถึงยอมสละความถูกต้องแบบเป๊ะ (consistency) เพื่อแลกกับความเร็ว/availability** ได้

ระบบ **distributed database** (ที่มีข้อมูลกระจายอยู่หลาย node) จะรักษาคุณสมบัติ 3 อย่างนี้พร้อมกันได้สูงสุดแค่ **2 ใน 3** เท่านั้น เวลาเกิดปัญหาการเชื่อมต่อระหว่าง node

|ตัวย่อ|คุณสมบัติ|ความหมาย|
|---|---|---|
|**C**|Consistency|ทุก node เห็นข้อมูล**ตรงกันเสมอ** ไม่ว่าจะอ่านจาก node ไหนก็ตาม|
|**A**|Availability|ระบบ**ตอบ request ได้เสมอ** แม้บาง node จะล่มหรือมีปัญหา|
|**P**|Partition Tolerance|ระบบยังทำงานต่อได้ แม้ network ระหว่าง node จะขาดการเชื่อมต่อ (partition)|

### ทำไมเลือกได้แค่ 2 ใน 3

ในระบบจริง **Network Partition (P) เกิดขึ้นได้เสมอ** (สาย network หลุด, node คุยกันไม่ได้ชั่วคราว) ดังนั้นทุกระบบ distributed จำเป็นต้องมี P ติดตัวไว้อยู่แล้ว

โจทย์จริงๆ เลยเหลือแค่ว่า **เมื่อเกิด partition ขึ้นมา ระบบจะเลือกรักษา C หรือ A** ไว้:

- **เลือก C (Consistency) ทิ้ง A** → ถ้า node บางส่วนคุยกันไม่ได้ ระบบจะ**ปฏิเสธการตอบ request** ชั่วคราว เพื่อไม่ให้ข้อมูลที่ส่งกลับไปผิดพลาด รอจน sync กันเสร็จก่อนค่อยตอบ
- **เลือก A (Availability) ทิ้ง C** → ระบบยัง**ตอบ request ได้เสมอ** แต่ข้อมูลที่ตอบกลับอาจไม่ล่าสุด 100% (บาง node อาจยังไม่ sync ข้อมูลใหม่)

> [!tip] สรุปแบบเข้าใจง่าย เมื่อ network มีปัญหา คุณเลือกได้แค่ "ตอบช้าแต่ถูกเป๊ะ" (CP) หรือ "ตอบเร็วแต่อาจไม่ล่าสุด" (AP)

### ตัวอย่างการจัดกลุ่ม CP / AP

| กลุ่ม  | เน้น                                |
| ------ | ----------------------------------- |
| **CP** | ข้อมูลถูกต้องเป๊ะ ยอมรอ/ตอบช้าได้   |
| **AP** | ตอบเร็วเสมอ ยอมข้อมูลไม่ sync ทันที |

## 5. สถานการณ์ไหนควรเลือกแบบไหน

### 5.1 เลือกตามลักษณะของข้อมูล/feature นั้นๆ

| ลักษณะข้อมูล / Feature                           | ควรใช้    | เหตุผล                                       | ตัวอย่าง                         |
| ------------------------------------------------ | --------- | -------------------------------------------- | -------------------------------- |
| ข้อมูลมีความสัมพันธ์ซับซ้อน ต้อง join หลาย table | **SQL**   | ต้องการความถูกต้องเวลาข้อมูลอ้างอิงกัน       | Order, Payment, Inventory        |
| ข้อมูลการเงิน/transaction ที่พลาดไม่ได้          | **SQL**   | ต้องการ ACID เต็มรูปแบบ                      | ระบบธนาคาร, ยอดเงินในกระเป๋า     |
| Schema ค่อนข้างคงที่ ไม่เปลี่ยนบ่อย              | **SQL**   | ออกแบบ table ล่วงหน้าได้ ไม่ต้องยืดหยุ่นมาก  | ข้อมูล user account หลัก         |
| ต้องทำ aggregation ซับซ้อน                       | **SQL**   | SQL query ทำ JOIN/GROUP BY ได้ทรงพลังกว่า    | Dashboard, สรุปยอดขาย            |
| Schema ไม่แน่นอน แต่ละ record หน้าตาไม่เหมือนกัน | **NoSQL** | ไม่ต้องกำหนด structure ตายตัวล่วงหน้า        | Log, JSON payload จาก API ภายนอก |
| ต้องการอ่าน/เขียนเร็วมาก แบบไม่ join             | **NoSQL** | เก็บเป็น object เดียวจบ ไม่ต้องรวมหลาย table | Cache, session, real-time feed   |
| ข้อมูลจะโตระดับ Big Data ต้อง scale แนวนอน       | **NoSQL** | เพิ่ม server ราคาถูกได้เรื่อยๆ               | Log เก็บระยะยาว, event data      |
| ยอมรับได้ถ้าข้อมูล sync ช้าหน่อย (ไม่ critical)  | **NoSQL** | ใช้แนวทาง AP ได้ ไม่กระทบธุรกิจ              | จำนวน like, view count           |

### 5.2 ถ้าเข้าเงื่อนไขทั้งคู่พร้อมกัน: ใช้ลำดับความสำคัญตัดสิน

บางข้อมูลอาจเข้าเงื่อนไขทั้งสองฝั่ง (เช่น ข้อมูลเยอะมาก **และ** ต้องแม่นยำสุดๆ) ให้ไล่ถามตามลำดับนี้ ข้อไหนตอบก่อน ให้ยึดข้อนั้นเป็นหลัก:

1. **พลาดแล้วเสียหายจริง (เงิน, transaction, stock) ไหม?** → ใช่ = **SQL ก่อนเสมอ** ไม่ว่าข้อมูลจะเยอะแค่ไหนหรือ schema จะยืดหยุ่นแค่ไหนก็ตาม (ความถูกต้องมาก่อน)
2. **ต้อง join ข้ามหลาย entity เพื่อให้ข้อมูลมีความหมายไหม?** → ใช่ = **SQL** (ถ้าแยกเป็น NoSQL จะต้อง join เองในโค้ด ซับซ้อนกว่าเดิม)
3. **ถ้าผ่าน 2 ข้อแรกมาแล้วไม่เข้าเงื่อนไข** ค่อยดูเรื่อง scale/ความเร็ว/schema ยืดหยุ่น → ถ้าสำคัญ = **NoSQL**

> [!tip] ถ้าสงสัยว่า "ได้ทั้งคู่เลย" → เช็คก่อนว่าเรื่อง **ความถูกต้อง/ความสัมพันธ์ของข้อมูล** สำคัญกว่าไหม ถ้าสำคัญ ให้เอียงไปทาง SQL ไว้ก่อน เพราะเราแก้ปัญหาเรื่อง scale ทีหลังได้ง่ายกว่าแก้ปัญหาข้อมูลผิดพลาด/ไม่สอดคล้องกัน

### 5.3 ในความเป็นจริง ไม่ต้องเลือกแค่อันเดียวสำหรับทั้งระบบ

ระบบจริงส่วนใหญ่ใช้**ทั้งสองแบบร่วมกัน** (Polyglot Persistence) โดยแยกใช้ตาม feature ไม่ใช่เลือกให้ทั้งแอป เช่น e-commerce หนึ่งระบบ:

- **PostgreSQL** → เก็บ order, payment, user account (ต้องแม่นยำ, มีความสัมพันธ์)
- **Redis** → เก็บ session, cart ชั่วคราว, cache (ต้องเร็ว)
- **MongoDB** → เก็บ product review, log (schema ไม่แน่นอน)
