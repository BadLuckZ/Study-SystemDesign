สมมติว่าเรามี Service A ที่ต้องรอให้เหตุการณ์บางอย่างเกิดขึ้นที่ Service B (เช่น งานที่ใช้เวลานานประมวลผลเสร็จ) ก่อน Service A จึงจะสามารถเริ่มงานได้ คำถามคือ A จะรู้ได้ยังไงว่าเสร็จแล้ว

ครั้นจะให้ A คอยยิงถาม B ซ้ำๆ ทุกกี่วินาทีว่า "เสร็จยัง เสร็จยัง" ก็เปลือง resources เพราะส่วนใหญ่ก็ได้กลับมาว่ายัง Webhook แก้ปัญหานี้ด้วยการ**กลับทิศ** โดยแทนที่ให้ A คอยถาม ก็เปลี่ยนเป็นให้ B เป็นคนมาบอก A เองตอนมีเหตุการณ์ดังกล่าวเกิดขึ้นที่ B

![[webhook_overview.png]]

มักเรียก Webhook ว่า "Reverse API" เพราะปกติเราเป็นคนเรียก API ของคนอื่น แต่ Webhook กลับกัน คือเราเปิด URL ทิ้งไว้ให้คนอื่นเรียกเรา หรือจะเปรียบว่า Polling เหมือนโทรถามซ้ำๆ ว่าของถึงยัง ส่วน Webhook เหมือนสั่งของแล้วให้เขาโทรมาบอกตอนของถึงก็ได้

### 2. Webhook ทำงานยังไง

Webhook ก็คือ **HTTP Request (มักเป็น POST) ที่ Server ฝั่งผู้ให้บริการยิงมาหา URL ที่เราเตรียมไว้** ตอนเกิดเหตุการณ์ที่เราสนใจ

มีขั้นตอนหลักสองช่วง

**ช่วง Setup (ทำครั้งเดียว)**: เราไปลงทะเบียนบอกผู้ให้บริการว่า "ถ้าเกิดเหตุการณ์ X ให้ยิงมาที่ URL นี้นะ" เช่น `https://myapp.com/webhooks/payment` โดยที่ URL นี้คือ Endpoint ที่เราต้องเปิดรอไว้ให้ผู้ให้บริการยิง Request เข้ามาหาเราได้

**ช่วงเกิดเหตุการณ์จริง**: พอเหตุการณ์ X เกิดขึ้น ผู้ให้บริการจะยิง POST มาที่ URL นั้นพร้อมข้อมูลของเหตุการณ์ (payload) ในรูปแบบ JSON ระบบเราก็อ่าน payload แล้วเอาไปประมวลผลต่อ

จุดที่ต้องเข้าใจคือ **Webhook Endpoint ของเราต้องเข้าถึงได้จาก Internet** (Public URL) เพราะผู้ให้บริการต้องยิงเข้ามาถึง ต่างจากตอนเราเรียก API คนอื่นที่เราเป็นฝ่ายยิงออก

### 3. เรื่องที่ต้องระวัง

เพราะ Webhook คือการเปิด URL ให้คนนอกยิงเข้ามา มันเลยมีเรื่องต้องระวังเป็นพิเศษ

1. **ต้องยืนยันว่าคนยิงมาคือตัวจริง** ในเมื่อ URL เปิดรับ Request จาก Internet ใครก็ยิงมั่วมาได้ ผู้ให้บริการที่ดีจึงมักแนบ **Signature** มาใน Header (เซ็นด้วย Secret ที่แลกกันไว้ตอน Setup) เราต้องตรวจ Signature ก่อนเชื่อ payload ไม่งั้นคนร้ายยิง Webhook ปลอมมาหลอกได้ (เหมือนการเซ็น JWT ใน [[01 Access Token|Access Token]] คือใช้ Secret ที่มีแค่สองฝั่งรู้มาพิสูจน์ว่าของจริง)

2. **ต้องรองรับการยิงซ้ำ (Idempotency)** ผู้ให้บริการหลายเจ้าการันตีแค่ "at-least-once" คือยิงอย่างน้อยหนึ่งครั้ง ซึ่งอาจยิง Webhook เดียวกันมาซ้ำได้ (เช่นตอน network มีปัญหาแล้ว retry) ระบบเราต้องออกแบบให้ประมวลผล event เดิมซ้ำได้โดยไม่พัง มักใช้ event ID เช็คว่าเคยรับแล้วหรือยัง

3. **ต้องตอบกลับเร็ว** ผู้ให้บริการมักคาดหวังให้เราตอบ `200 OK` เร็วๆ (ในไม่กี่วินาที) ถ้าเราไปทำงานหนักค้างไว้นานแล้วตอบช้า เขาอาจคิดว่า fail แล้ว retry มาซ้ำ ทางที่ดีคือ **รับ Webhook แล้วโยนเข้า Queue ให้ประมวลผลทีหลัง** แล้วรีบตอบ 200 กลับไปก่อน -> สามารถทำได้ผ่านการสร้าง Message Queue สำหรับเก็บ Request ที่ถูกยิงมาจากผู้ให้บริการ

4. **ต้องมีแผนสำรองถ้า Webhook พลาด** เพราะ Webhook วิ่งผ่าน network ที่ไม่ชัวร์ 100% บาง event อาจหายไป ระบบที่สำคัญ (เช่นเรื่องเงิน) จึงมักมี Polling เป็นตัวสำรองไว้เช็คซ้ำ หรือมีระบบ reconciliation คอยกระทบยอดว่าตกหล่นไหม

### 4. Webhook เทียบกับวิธีอื่น

Webhook เป็นหนึ่งในหลายวิธีที่ Client รู้เรื่องความเปลี่ยนแปลงจาก Server ลองเทียบให้เห็นภาพ

|วิธี|ใครเริ่ม|เหมาะกับ|
|---|---|---|
|**Polling**|Client ถามซ้ำๆ|ง่าย แต่เปลืองและช้า|
|**Webhook**|Server ยิงมาบอก|event ที่เกิดนานๆ ครั้ง ไม่ต้องการ connection ค้าง|
|**WebSocket**|เปิด connection ค้างสองทาง|real-time ต่อเนื่อง เช่น chat|

จุดที่ Webhook ต่างจาก WebSocket คือ Webhook **ไม่ได้เปิด connection ค้างไว้** เป็นการยิง Request มาเป็นครั้งๆ ตอนมี event เท่านั้น จึงเบากว่าและเหมาะกับเหตุการณ์ที่นานๆ เกิดที (เช่น payment เสร็จ, ไฟล์ประมวลผลเสร็จ) ส่วน WebSocket เหมาะกับข้อมูลที่ไหลถี่และต่อเนื่องมากกว่า
