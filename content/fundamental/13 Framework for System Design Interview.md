สภาพของการสัมภาษณ์จะเป็นประมาณว่า... เข้าไปนั่งสัมภาษณ์ ละก็มีผู้สัมภาษณ์ราวๆ 1-2 คน ที่เป็น developer ของบริษัท จังหวะนั้นเราก็เกร็งๆ พอสมควรละ พอเริ่มสัมภาษณ์ปุ๊ป โดนโยนโจทย์มาว่า "เราลองออกแบบระบบ xxx หน่อยได้มะ?" เสร็จคำถามปุ๊ป เราก็หัวโล่งเลย ไม่รู้จะไปต่อยังไงดี แบบ..."ห่ะ ถามไรวะ" ไม่ก็ "ใครมันจะไปคิดทันในเวลาแค่นี้วะ" ละก็แห้วสัมภาษณ์รอบนั้นไป...

ปัญหาก็มีได้หลายสาเหตุนะ ทั้งการที่เรายังไม่รู้จัก concept สำคัญสำหรับระบบนี้ หรือการที่เรารู้จัก concept แหละ แต่ไม่รู้ / คาดไม่ถึงว่ามันจะเกี่ยว หรือเรารู้ แต่ว่าเราพูดไม่รู้เรื่อง รู้เรื่องแค่กับตัวเองว่าทำยังไง แต่พูดให้คนสัมภาษณ์เข้าใจไม่ได้ หรืออาจจะมีสาเหตุอื่นๆ อีกอ่ะนะ

![[meme_01.png]]

คือต้องบอกว่า เป้าประสงค์จริงๆ ของ System Design Interview อ่ะ ไม่ใช่การหา Solution ที่มันจะต้องเป็น Final Solution เลย แต่ว่าเป็นการหา Solution ที่มันเพียงพอต่อความต้องการของคนสัมภาษณ์ เพราะในการทำงานจริงๆ อ่ะ ก็มีโอกาสที่เราจะปรับ Solution ตามหน้างานอยู่แล้ว นาทีสัมภาษณ์ตรงนี้จึงเอาแค่ว่า Solution อะไรที่คนสัมภาษณ์เค้าต้องการ ก็เพียงพอแล้วต่อการที่จะเพิ่มโอกาสผ่านสัมภาษณ์

เพราะการนำมาซึ่ง Solution ที่ผู้สัมภาษณ์พอใจได้เนี่ยมันสะท้อน skills หลายๆ อย่างของ candidate คนนั้นแล้วอ่ะนะ ทั้งการสื่อสาร การทำงานภายใต้แรงกดดัน การแก้ปัญหา และอื่นๆ ที่สมควร มันเพียงพอแล้วจริงๆ

> [!tip] สิ่งที่คนสัมภาษณ์มองหาจริงๆ ไม่ใช่แค่ "Technical Skill" อย่างเดียว เค้ามองหาว่าเรา collaborate กับเค้าได้ไหม ทำงานภายใต้ความกดดันได้ไหม แก้ปัญหาที่ยัง"คลุมเครือ" (ambiguous) ได้อย่างมีเหตุผลไหม รวมถึงถามคำถามที่ดีเป็นไหม ส่วน Red Flag ที่คนสัมภาษณ์มักมองหาคือการ Over-engineer (คิดเผื่อเกินความจำเป็นจนหลงประเด็น) กับความดื้อ/มองโลกแคบ (ไม่รับ feedback)

ดังนั้น แล้วเราจะทำยังไงให้ไม่ล่กกับ System Design Interview แล้วผ่านไปได้ด้วยดีกันนะ....

## 1. ถามรายละเอียดของ Scope งาน

เราจะเริ่มออกแบบระบบได้ไงถ้าเรายังไม่เข้าใจมากพอว่าอยากให้ระบบนี้ทำอะไรได้อ่ะ

สิ่งที่ควรทำเป็นอย่างแรกพอได้โจทย์มาคือ ถามคำถามเพื่อทำความเข้าใจ requirement กับ assumption ก่อน ถ้าคนสัมภาษณ์ตอบคำถามตรงๆ ไม่ได้ เค้าอาจจะบอกให้เรา "สมมติเอง" ก็ได้ ก็สามารถกำหนดในแบบที่เราถนัดก็ได้

คำถามที่ควรถามมีประมาณนี้:
- Feature อะไรบ้างที่ต้องมีจริงๆ (ไม่ใช่ทุก Feature ที่เป็นไปได้)
- User ของ Product นี้มีประมาณกี่คน
- บริษัทคาดว่าจะ Scale เร็วแค่ไหน (3 เดือน, 6 เดือน, 1 ปี ข้างหน้า)

ตัวอย่างเช่น ถ้าโจทย์คือ "ออกแบบ News Feed System" บทสนทนาอาจจะเป็นแบบนี้:

> **เรา:** เป็น Mobile App หรือ Web App หรือทั้งคู่ครับ? **ผู้สัมภาษณ์:** ทั้งคู่เลย
> 
> **เรา:** Feature ที่สำคัญที่สุดคืออะไรครับ? **ผู้สัมภาษณ์:** ความสามารถในการโพสต์ และดู Feed ของเพื่อน
> 
> **เรา:** Feed เรียงตามเวลาล่าสุดไปเก่าสุด (reverse chronological) หรือมี Order พิเศษครับ (เช่นให้น้ำหนักโพสต์เพื่อนสนิทมากกว่า)? **ผู้สัมภาษณ์:** เอาง่ายๆ ก่อน เรียงตามเวลาล่าสุดไปเก่าสุดพอ
> 
> **เรา:** User หนึ่งคนมีเพื่อนได้สูงสุดกี่คนครับ? **ผู้สัมภาษณ์:** 5,000 คน
> 
> **เรา:** Traffic ประมาณเท่าไหร่ครับ? **ผู้สัมภาษณ์:** DAU (Daily Active User) 10 ล้านคน
> 
> **เรา:** Feed มีแค่ Text หรือมี Image/Video ด้วยครับ? **ผู้สัมภาษณ์:** มีทั้ง Image และ Video เลย

## 2. Sketch ภาพรวมระบบคร่าวๆ ก่อน แล้วค่อยขอความเห็นจากผู้สัมภาษณ์

พอเราเข้าใจ Scope แล้ว ขั้นต่อไปคือการ Draft Design แล้วเอาไปคุยกับผู้สัมภาษณ์ ให้มองเค้าเป็น Teammate ไม่ใช่ผู้สัมภาษณ์ เพราะผู้สัมภาษณ์ที่ดีชอบพูดคุยและ Involve ไปกับ Design ของเราด้วย

![[system_design_news_feed.png]]

สิ่งที่ทำในขั้นนี้:

- วาด Box Diagram ของ Component หลักๆ (Client, Services, Web Server, Database, Cache, CDN, Message Queue เป็นต้น)
- ทำ **Back-of-the-envelope Calculation** เพื่อเช็คว่า Design ที่วาดไว้รองรับ Scale ที่คุยกันไว้ได้จริงไหม พูดออกมาดังๆ ด้วยนะ อย่าคิดเงียบๆ คนเดียว
- ถ้าเป็นไปได้ ลองไล่ Use Case จริงๆ สักสองสามอันดู เพราะบางที Use Case พวกนี้แหละที่จะช่วยให้เราเจอ Edge Case ที่ยังไม่เคยคิดถึงมาก่อน

จุดที่มักงงกันคือ "แล้วต้องลง API Endpoint หรือ Database Schema เลยมะ?" คำตอบคือ **แล้วแต่โจทย์** ถ้าโจทย์กว้างมากแบบ "ออกแบบ Google Search" การลงเบอร์นั้นอาจจะ Low-level เกินไปในช่วงนี้ แต่ถ้าโจทย์เฉพาะทางกว่า เช่น "ออกแบบ Backend ของเกม Poker หลายผู้เล่น" การลงรายละเอียดขนาดนั้นอาจจำเป็นเลย ทางที่ดีที่สุดคือคุยกับผู้สัมภาษณ์ตรงๆ ว่าเค้าอยากให้ลงลึกระดับไหน

## 3. เจาะลึกในจุดที่สำคัญ (Design Deep Dive)

ถึงจุดนี้ เราควรจะมีคำตอบสำหรับสิ่งเหล่านี้แล้วอ่ะนะ:

- ตกลงกับผู้สัมภาษณ์แล้วว่า Scope และเป้าหมายโดยรวมคืออะไร
- มี Blueprint ของ High-level Design คร่าวๆ แล้ว
- ได้ Feedback จากผู้สัมภาษณ์เกี่ยวกับ Design นั้นแล้ว
- พอจะเดาได้แล้วว่าควร Focus ตรงไหนต่อจาก Feedback ที่ได้มา

ขั้นตอนนี้คือการทำงานร่วมกับผู้สัมภาษณ์เพื่อเลือกว่า Component ไหนใน Architecture ที่ควรเจาะลึกก่อน บางทีผู้สัมภาษณ์ก็จะ hint มาตรงๆ ว่าอยากคุยส่วนไหน บางทีก็ต้องการฟัง Performance Characteristic (คุณสมบัติด้าน Performance) เช่น Bottleneck (จุดคอขวดของระบบ) อยู่ตรงไหน หรือ Resource Estimation ประมาณไหน

ตัวอย่างเช่น ถ้าเป็นโจทย์ URL Shortener การเจาะลึกเรื่อง Hash Function (ฟังก์ชันที่แปลง URL ยาวให้เป็น URL สั้น) จะน่าสนใจมาก หรือถ้าเป็นโจทย์ Chat System เรื่อง Latency กับการทำ Online/Offline Status ก็เป็นหัวข้อที่น่าคุยเหมือนกัน

> [!warning] ระวังเรื่อง Time Management อย่าหลงไปกับรายละเอียดปลีกย่อยที่ไม่ได้ช่วยโชว์ Ability ของเรา เช่น ถ้าเป็นโจทย์ News Feed แล้วเราลงไปอธิบาย Algorithm การจัดอันดับ Feed แบบละเอียดยิบ (คล้ายๆ EdgeRank ของ Facebook) นี่คือเสียเวลาโดยใช่เหตุ เพราะมันไม่ได้ช่วยพิสูจน์ว่าเราออกแบบระบบที่ Scale ได้เป็นยังไง

## 4. สรุปปิดท้าย พูดถึงจุดที่ยังพัฒนาต่อได้

ช่วงสุดท้ายนี้ ผู้สัมภาษณ์อาจถามคำถามต่อยอด หรือให้อิสระเราคุยเรื่องอื่นเพิ่มได้ ทิศทางที่ควรเตรียมไว้:

- ผู้สัมภาษณ์อาจอยากให้เราชี้จุด Bottleneck ของระบบที่เราออกแบบมา แล้วบอกว่าจะแก้ยังไง - **อย่าบอกว่า Design ของเราสมบูรณ์แบบไม่มีจุดต้องแก้เด็ดขาด** เพราะมันไม่มีระบบไหนสมบูรณ์แบบจริงๆ นี่คือโอกาสโชว์ Critical Thinking และทิ้งท้ายด้วยความประทับใจ
- สรุป Design ทั้งหมดให้ผู้สัมภาษณ์ฟังอีกรอบ โดยเฉพาะถ้าเราเสนอหลาย Solution ไปตลอด Session (การสรุปช่วยรีเฟรชความจำผู้สัมภาษณ์หลัง Session ยาวๆ ได้ดี)
- พูดถึง Error Case ที่น่าสนใจ (Server ล่ม, Network หลุด ฯลฯ)
- พูดถึงเรื่อง Operation เช่น จะ Monitor Metric/Error Log ยังไง จะ Roll out ระบบยังไง
- คิดต่อว่าถ้าระบบต้อง Scale ต่อไปอีก (เช่นจาก 1 ล้าน User เป็น 10 ล้าน User) ต้องปรับอะไรเพิ่ม
- เสนอ Refinement อื่นๆ ถ้ามีเวลาเพิ่ม
