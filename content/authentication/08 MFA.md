MFA หรือ Multi-factor Authentication ก็ตรงตัวนะ หรือการยืนยันตัวตนด้วยหลักฐานมากกว่า 1 ประเภท แล้วมันมีกี่ประเภทกันนะ หลักๆ ก็มี 3 ประเภท คือ
1. Something you know เช่น Password หรือ PIN
2. Something you have เช่น Smartphone, Ipad หรือ Security Key 
3. Something you are เช่น ลายนิ้วมือ, ม่านตา หรือ ใบหน้า

สำคัญคือ ต้องมาจากหลายประเภท ไม่ใช่หลายครั้ง เช่นการถาม Password หลายๆ ครั้ง อันนี้ไม่ใช่ MFA เป็นต้น ข้อดีของมันก็คือถึงต่อให้ attacker จะขโมย Password หรือ PIN หรืออะไรก็ตามที่ต้องรอ User กรอกอ่ะ พอเจอการขอ verify ด้วยข้อมูลประเภทอื่นขึ้นมาก็ไปต่อไม่ได้ละ ก็ปลอดภัยขึ้นเยอะ

ทีนี้เราจะมาดูกันทีละประเภท -> Something you know นี่ Basic ละ มีกันทั่วๆ ไป ส่วน Something you are มันจะออกไปทาง Biometrics หน่อยๆ ก็อธิบาย concept ทาง software ยากอยู่ เพราะงั้นเราจะ Focus ถึง Something you have ละกันว่าทำยังไงให้มันสามารถนำมาใช้เป็นข้อมูลประเภทหนึ่งในการ verify ตัวตนของเราได้

## 1. Out-of-band OTP

![[auth_mfa_otp.png]]

Out-of-band OTP คือการส่ง OTP ผ่านช่องทางแยกจากตัวแอป เช่น มาทาง SMS หรือ Email เป็นต้น

ส่วนขั้นตอนทำยังไง คร่าวๆ ก็ให้ระบบสุ่มสร้าง OTP ขึ้นมา แล้วกำหนดเพิ่มเติมว่า OTP นี้ใช้ได้ถึงเวลาไหน แล้วเก็บข้อมูลทั้ง OTP (ในลักษณะของ Hash เพื่อความปลอดภัย), เวลา และ User ID ไว้ใน Database จากนั้นก็ร่างข้อความสำหรับส่ง จะเป็น Email Template หรือ SMS Template ก็ตามแต่จะใช้งาน จากนั้นก็ส่งข้อมูล รอให้ User กรอก

แต่ด้วยความที่ระยะเวลาของ OTP แบบนี้จะนาน เพราะงั้นจะมีวิธีการเพิ่มเติมเพื่อทำให้ปลอดภัย คือการทำ limit ว่า user จะกรอก OTP ได้สูงสุดกี่ครั้ง รวมถึงถ้าจะขอ OTP ใหม่ ก็จะมีการกำหนดไว้ว่าขอ OTP ใหม่ได้เมื่อเวลาผ่านไป xx นาทีหลังกดขอ OTP เป็นต้น

### 1. Limit จำนวนครั้งที่กรอกผิด

ทำได้ด้วยการเพิ่ม `attempt_count` เข้าไปในตาราง OTP แล้วนับขึ้นทุกครั้งที่กรอกผิด แล้ว Flow ตอน User กรอก OTP เข้ามาจะเป็นดังนี้
1. ดึงข้อมูล OTP ของ User นั้นจาก Database (เวลา User นั้น Login สำเร็จ ก็จะมี [[01 Access Token|Access Token]] กับ [[02 Refresh Token|Refresh Token]] มาให้แล้ว ทำให้รู้ได้ว่า User คนนี้มี User ID อะไร)
2. เมื่อ User กรอก OTP ส่งเข้ามา ระบบจะเช็คว่า User นี้มี `attempt_count` เกิน Limit (เช่น 5) หรือยัง ถ้าเกินแล้ว → ปฏิเสธทันที ไม่ต้องเทียบ OTP ด้วยซ้ำ
3. ถ้ายังไม่เกิน ค่อยเทียบ OTP ที่กรอกมากับที่เก็บไว้
	- ถ้าผิด → `attempt_count` + 1 แล้วบันทึกกลับ
	- ถ้าถูก → revoke OTP นั้นทันที

### 2. Limit การขอ OTP ใหม่ (Cooldown)

ทำได้ด้วยการเก็บ เวลาที่ขอ OTP ครั้งล่าสุด ไว้ (`last_sent_at`) แล้วตอน User กดขอใหม่ ก็เทียบว่าผ่านมาถึงเวลาที่กำหนดหรือยัง ทำให้ Flow ตอน User กดขอ OTP ใหม่ เป็นดังนี้
1. ดึง `last_sent_at` ของ User นั้นมา
2. คำนวณว่า เวลาปัจจุบัน - `last_sent_at` ผ่านไปเกิน Cooldown (เช่น 60 วินาที) หรือยัง
	- ถ้ายังไม่ถึง → ปฏิเสธ พร้อมบอกว่าต้องรออีกกี่วินาที ส่งกลับมาให้ frontend นับเวลาให้ User เห็น
	- ถ้าถึงแล้ว → สร้าง OTP ใหม่ ส่ง แล้วอัปเดต `last_sent_at` เป็นเวลาปัจจุบัน

## 2. TOTP

ด้วยความที่ OTP มันให้เวลานาน ก็เสี่ยงว่าจะโดนเอาไปใช้โดยคนอื่น แถมมันสวมรอยโดยคนอื่นได้ด้วย แบบว่า... attacker ที่มันรู้ Email Password เราอยู่แล้วมันก็สามารถเข้าถึง Platform ที่ App ส่ง OTP ให้ไปได้อยู่แล้ว แล้วเราจะทำไงดี คำตอบคือ OTP Upgrade Version อย่าง TOTP นั่นเอง

TOTP หรือว่า Time-based One-Time Password หรือเป็นรหัสผ่านที่ใช้ได้ครั้งเดียว และมีการจับเวลาเอาไว้ว่ามีเวลาอีกกี่วินาทีที่ยังสามารถใช้ได้

![[auth_mfa_totp_microsoft_authenticator.png]]

ก็จะเห็นว่าแต่ละ Application ก็จะมี Password เป็นของตัวเอง ละก็จับเวลาของใครของมันไป (คือเลขเวลามันแยกของใครของมันเลยนะ ในแบบเห็นว่าเหลืออีก 14 วิเหมือนกันแต่ของจริงจะต่างกันก็ทำได้)

คำถามที่สำคัญคือ แล้วตัว App Authenticator นี้ กับ Server ของแต่ละ Program เช่น TOTP สำหรับ Dropbox กับ Dropbox Server มันเห็นเลขเวลาตรงกันได้ไง ทั้งๆ ที่เราไม่ได้เชื่อมต่อกันเลย ไหนยังจะการที่พอ Password หมดเวลาแล้ว ก็ได้ TOTP ใหม่มาแทบจะในทันทีอีก

คำตอบคือ ตอนที่เราสมัครใน Authenticator ว่าจะมี App อะไรบ้างที่ใช้ TOTP เมื่อเราลงทะเบียน App ที่ใช้ Authenticator สำเร็จ เช่นสมมติว่าเราลงทะเบียน Dropbox ไว้ละกัน Dropbox Server จะสร้าง Secret ขึ้นมาสำหรับ User ดังกล่าว แล้วส่ง Secret นั้นมาให้ Authenticator ด้วย เท่ากับว่าก็จะมี Secret ในทั้ง 2 ที่

มีอีกส่วนนึงที่ต้องใช้ในการสร้าง TOTP ก็คือเวลา ณ ปัจจุบัน (ความต่างทางวินาทีระหว่างเวลาปัจจุบัน กับ 1 Jan 1970 UTC) ที่หารด้วย 30 แล้วปัดเศษลง เพื่อให้เกิด TOTP ที่แตกต่างกันไปตามช่วงเวลา 

จากนั้นก็นำทั้ง 2 ส่วนมาเข้า Hash Function ก็จะได้ออกมาเป็น TOTP ที่ทั้ง Application Server และ Authentication Server เห็นตรงกันแล้ว (แต่ว่า User ยังสามารถใช้ TOTP ที่เวลาหมดไปแล้วได้อีกนิดนึงนะ เพราะด้วยความ 2 Server แหละ เวลาจะตรงกันเป๊ะเลยก็ยากไป)

## 3. Backup Code

แล้วถ้ามือถือหายอ่ะ... Authenticator ก็ใช้ไม่ได้ละป่ะ แล้วจะทำไงดีถึงจะ verify ตัวเองได้ คำตอบคือ Backup Code นั่นเอง

Backup Code คือ รหัสสำรองที่ระบบสร้างเอาไว้ให้ User ในกรณีที่ไม่สามารถเข้าถึงอุปกรณ์หรือวิธีการยืนยันตัวตนหลักได้ เช่น มือถือหาย, เครื่องพัง หรือไม่สามารถเปิด Authenticator ได้ ตอนที่ User เปิดใช้งาน MFA ระบบจะสร้าง Backup Code ขึ้นมาหลายชุด เช่น 10 รหัส แล้วแสดงให้ User เก็บไว้ในที่ปลอดภัย

ตัวอย่างเช่น

```
7K4P-92XM
Q8TZ-31FA
M6WR-84LP
...
```

แต่ละ Code จะสามารถใช้ได้ **เพียงครั้งเดียว** เท่านั้น เวลาจะใช้งานก็จะมี Flow ก็ประมาณนี้
1. ตอนเปิดใช้งาน MFA ระบบ Generate Backup Codes ให้ User
2. ระบบเก็บ Backup Code เหล่านั้นเป็น **Hash** ใน Database ส่วน User เก็บ Backup Codes ไว้ในที่ปลอดภัย ที่ตนเองสามารถเข้าถึงได้
3. ตอน Login หลังจากกรอก Password สำเร็จ ระบบจะมีการขอ MFA
4. User สามารถเลือกใช้ Backup Code ได้ จากนั้นก็เลือกกรอก Backup Code ที่ยังไม่เคยใช้มาก่อน
5. Server นำ Code ที่ User กรอกมา Hash แล้วนำไปเทียบกับ Code ที่ยังไม่ถูกใช้
	- ถ้าตรงกัน → Authentication สำเร็จ และ Revoke Backup Code นั้นทันที
	- ถ้าไม่ตรงกัน → ปฏิเสธ
