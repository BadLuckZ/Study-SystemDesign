## 1. ปัญหาตั้งต้น: ระบบจำได้ยังไงว่าใคร Login อยู่

HTTP เป็น Protocol ที่ไม่มี Memory หรือก็คือไม่สามารถจำได้ว่า Request ใดบ้างที่มาจาก User เดียวกัน แปลว่าแต่ละ Request ที่วิ่งเข้ามาที่ Server ถือเป็นเหตุการณ์อิสระที่ไม่รู้จักกัน ทำให้ Server ไม่มีทางรู้เลยว่า Request ที่เพิ่งเข้ามานี้มาจาก User คนเดียวกับ User ที่ขอ Request เมื่อ 5 วินาทีก่อนหรือเปล่า

ปัญหาจึงกลายเป็นว่า หลังจาก User พิสูจน์ตัวตนด้วย Username/Password ไปแล้วครั้งหนึ่ง 

จะทำยังไงให้ Request ครั้งต่อๆ ไปไม่ต้องพิสูจน์ตัวตนใหม่ทุกครั้ง??

Solution ที่ทำได้ คือให้ Server มอบหลักฐานบางอย่างให้ Client เก็บไว้หลัง Login สำเร็จ แล้วให้ Client แนบหลักฐานนั้นกลับมาทุกครั้งที่ยิง Request หลักฐานชิ้นนี้เรียกว่า Token ทำให้ Server สามารถใช้หลักฐานตัวนี้เพื่อระบุได้ว่า Client คนนี้ขอ Request มา

## 2. Access Token คืออะไร

Access Token คือหลักฐานยืนยันตัวตนที่ได้รับจาก Server ที่ Client แนบไปกับทุก Request เพื่อบอก Server ว่าตัวเองเป็นใคร และมีสิทธิ์อะไร โดย Access Token นี้จะถูกส่งผ่าน HTTP Header ในรูปแบบที่เรียกว่า Bearer Token

```http
GET /api/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0In0.dBjftJeZ4CVP...
```

Pattern การแนบ Token ไปใน HTTP Header จะส่งผล 2 อย่าง
1. Token ต้องถูกส่งผ่าน HTTPS เสมอ เพราะถ้าดักจับได้กลางทางก็เอาไปใช้ได้เลย การใช้ HTTPS มันก็ยังมีการ encrypt ที่พอช่วยให้ข้อมูลของ User พอปลอดภัยได้บ้าง แต่ก็ยังไม่พออ่ะนะ
2. ถ้า Token หลุด ระบบไม่มีทางแยกออกว่าคนที่ใช้อยู่เป็นเจ้าของตัวจริงหรือคนที่ขโมยมา ก็เป็นเรื่องที่อันตรายอ่ะนะ

## 3. JWT

Token ที่ใช้ identify User จะเป็นข้อความอะไรก็ได้ในทางทฤษฎี แต่รูปแบบที่นิยมที่สุดคือ **JWT (JSON Web Token)** ซึ่งเป็นมาตรฐานที่ทำให้ Token บรรจุข้อมูลไว้ในตัวเองได้ และตรวจสอบความถูกต้องได้โดยไม่ต้องพึ่งข้อมูลจากที่อื่น

JWT ประกอบด้วยข้อมูล 3 ส่วนที่คั่นด้วยจุด แต่ละส่วนมีหน้าที่ต่างกันชัดเจน
1. Header - ส่วนเกริ่น ประมาณว่าไว้ใช้บอกว่า สิ่งนี้คือ JWT นะ
2. Payload - เนื้อหา โดยจะเป็นรายละเอียดต่างๆ ที่ต้องการเก็บไว้ เช่น user id, role, exp
3. Signature - ลายเซ็น เป็นสิ่งที่ Server ใช้ในการเช็คว่า Token นี้ออกโดย Server นี้จริงๆ หรือไม่

![[auth_jwt_structure.png]]

>[!tip] Base64 ไม่ใช่การทำ Encryption
>Base64 เป็นแค่การเปลี่ยนรูปแบบข้อมูลให้ส่งผ่าน HTTP ได้สะดวก ใครที่ได้ Token ไปสามารถ Decode อ่านเนื้อหาข้างในได้ทันที เพราะงั้นเลยไม่ควรเก็บข้อมูลส่วนตัวไว้เด็ดขาด ควรมีแค่ของที่ระบุตัวตนพื้นฐานได้เท่านั้น เพื่อให้ Server สามารถระบุได้ว่าเราเป็นใคร

แล้ว Signature มันช่วยให้ Server รู้ได้ไงว่า Token นี้ออกโดยตัว Server เอง คำตอบคือการมี SECRET_KEY เข้าไปเป็นส่วนนึงของ Token ตามวิธีนี้

```ts
Signature = HMAC-SHA256(base64(Header) + "." + base64(Payload), SECRET_KEY)
```

ซึ่ง SECRET_KEY คือสิ่งที่ Developer กำหนด จะเป็น Text อะไรก็ได้ตามสะดวก ละจะมีแค่ Server เท่านั้นที่รู้ว่า SECRET_KEY คืออะไร ไม่มีทางที่ User จะรู้ได้ เลยทำให้ Server ตรวจสอบได้ว่า Token นี้ออกโดย Server หรือไม่ หรือเป็น Token ปลอม

## 4. Login Flow

![[auth_login_flow.png]]

1. ในหน้า Login เมื่อ User กรอก Email + Password เข้ามา ระบบก็ส่ง Email + Password ผ่าน API **POST** /login
2. ระบบหา User Information ผ่าน Email จากนั้นดึง Password ที่คู่กับ Email นั้นมา แล้วนำมาเทียบ Password ที่ User ส่งมา (Password ใน Database จะถูกทำเป็น Hash Password เพราะงั้น Password ที่ User ส่งมาก็ต้อง hash ก่อนที่จะเทียบค่าด้วย)
3. หากรหัสผ่านถูกต้อง ระบบก็จะดึงข้อมูลที่เหลือของ User ด้วย Email โดยดึงมาแค่ของที่จำเป็นต่อการระบุตัวตนในระบบ เช่น user id, role, เวลาที่ Token นี้จะหมดอายุการใช้งาน (exp) เป็นต้น แล้วนำข้อมูลเหล่านี้มาสร้างเป็น Payload
4. นำ Header ของ JWT Pattern กับ Payload มาสร้าง Signature ด้วย SECRET KEY ที่ Developer กำหนดขึ้นมา แล้วประกอบร่างเป็น Access Token ที่เป็น JWT Pattern ส่งคืน User ไป

## 5. Validate Flow

หลังจาก Client ได้ Token มาแล้ว ทุก Request ที่ยิงเข้ามา Server จะทำตามลำดับ 5 ขั้นตอนนี้

![[auth_validate_flow.png]]

1. ระบบจะเอา Token ที่แนบมาใน HTTP Header มาแยกเป็น 3 ส่วน คือ Header, Payload และ Signature ถ้าแยกไม่ได้ก็ Unauthorized
2. ระบบจะนำส่วน Header และ Payload มาคำนวณหา Signature เองก่อน
3. ระบบจะนำ Signature ที่ได้จาก 2. มาเทียบกับ Signature ใน 1. ถ้าไม่ตรงกันก็ Unauthorized
4. ระบบจะดูเนื้อหาใน Payload ว่าเป็น Token ที่หมดอายุหรือยัง ถ้าหมดแล้วก็ Unauthorized
5. ระบบดึงข้อมูลที่เหลือใน Payload แล้วตอบสนองกับเนื้อหาที่อ่านเจอ

สิ่งที่น่าสนใจ คือ **ไม่มีขั้นไหนที่ต้อง Query Database เลย** ทุกอย่างตรวจสอบได้จากตัว Token บวกกับ Secret Key ที่ Server ถืออยู่แล้ว รวมถึงต่อให้ Request จะวิ่งไปลงเครื่องไหนก็ตรวจ Token ได้เหมือนกันหมด ซึ่งเป็นข้อได้เปรียบใหญ่เมื่อเทียบกับการเก็บ Session ไว้ที่ Server

## 6. ปัญหาของ Access Token

Flow มันก็ดู Make Sense และตอบโจทย์ Stateless HTTP ดีนะ แต่ว่า Token ที่ถือข้อมูลของ User แบบนี้ ควรจะมีอายุการใช้งานนานแค่ไหนนะ? 

#### ถ้ามีอายุเยอะ

เช่น ตั้งไว้ 30 วันเพื่อให้ User ไม่ต้อง Login บ่อย ถ้า Token หลุดไปอยู่ในมือคนอื่น เขาจะสวมรอยเป็น User คนนั้นได้เต็มที่ 30 วัน แล้วระบบเองก็ไม่มีวิธีการระบุได้เลยด้วยว่าคนที่ใช้ Token นี้คือเจ้าของจริงๆ หรือว่าคนที่สวมรอยอยู่

หนักกว่านั้นคือ ระบบไม่สามารถหยุดการใช้งาน Token ที่ออกไปแล้วได้ ต้องรอให้ Token หมดอายุไปเอง ก็ทำให้คนที่สวมรอยแทนเรา ใช้งาน Account เราได้ถึง 30 วันเลย

### ถ้ามีอายุน้อย

เช่น ตั้งไว้ 15 นาทีเพื่อจำกัดความเสียหาย ความเสี่ยงของการโดนสวมรอยก็ลดลง แต่ User ต้องพิมพ์ Username และ Password ใหม่ทุก 15 นาที มันก็น่ารำคาญอ่ะนะ
