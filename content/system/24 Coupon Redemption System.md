วันนี้เราจะมาสร้างระบบคูปองกัน คือพวก "ลด 100 บาทเมื่อซื้อครบ 500 บาท", "ส่งฟรีเมื่อซื้อครบ 2,000 บาท" หรือ "Flash Sale คูปองลด 50% จำนวน 1,000 ใบ เที่ยงตรง" ที่เห็นกันในแอป E-Commerce, แอปธนาคาร หรือ Delivery App อย่าง Grab กับ LINE MAN นั่นแหละ

หน้าที่หลักคือ**แจกคูปองให้ไม่เกินจำนวน และให้คูปองแต่ละใบถูกใช้ได้แค่ครั้งเดียว**

ดูเผินๆ ก็เหมือนแค่ลบเลขธรรมดา แต่หลังบ้านซับซ้อนกว่าที่เห็นเยอะ และพอเป็นเรื่องเงินๆ ทองๆ ก็พลาดไม่ได้เลย จะเป็นไง มาดูกัน...

## 1. ถามรายละเอียดของ Scope งาน

Q1: ระบบนี้ใช้กับอะไรเหรอครับ? 
A1: แอป E-Commerce ที่มีคูปองหลายแบบ ทั้งร้านค้าออกเองและแพลตฟอร์มออกให้

Q2: คูปองมีแบบไหนบ้างครับ? 
A2: เอาหลักๆ 3 แบบ คือ ลดเป็นจำนวนเงิน (Fixed), ลดเป็นเปอร์เซ็นต์ (Percent) โดยมีเพดานส่วนลด และส่งฟรี (Free Shipping)

Q3: User ได้คูปองมายังไงครับ? 
A3: มี 2 ทาง คือกดเก็บ (Claim) ในแอปไว้ก่อน กับกรอก Code ตอน Checkout ซึ่ง Code มีทั้งแบบทุกคนใช้ Code เดียวกันอย่าง `NEWYEAR100` และแบบสุ่มแจกให้แต่ละคน

Q4: มีข้อจำกัดอะไรบ้างครับ? 
A4: จำนวนคูปองทั้งหมด, จำนวนต่อ User, ช่วงเวลา, ยอดขั้นต่ำ, สินค้าหรือหมวดที่ใช้ได้ และงบรวมของแคมเปญ

Q5: ใช้หลายคูปองใน Order เดียวได้มั้ยครับ? 
A5: ได้นะ เช่น คูปองร้านค้า 1 ใบ + คูปองแพลตฟอร์ม 1 ใบ + คูปองส่งฟรี 1 ใบ

Q6: ถ้า Order ถูกยกเลิกหรือคืนเงิน คูปองล่ะครับ? 
A6: ถ้ายกเลิกก่อนจ่ายหรือจ่ายไม่สำเร็จ ต้องคืนคูปอง ถ้าคืนเงินหลังจ่ายแล้ว ให้ขึ้นกับนโยบายของแคมเปญ

Q7: ระบบใหญ่ขนาดไหนครับ? 
A7: 10 ล้าน DAU และมี Flash Campaign ที่คูปองหมดในไม่กี่วินาทีเป็นประจำ

### Functional Requirement

- Admin / ร้านค้าสร้างแคมเปญและคูปองพร้อมเงื่อนไขได้
- User กดเก็บคูปอง และดูคูปองที่มีได้
- คำนวณส่วนลดให้เห็นในตะกร้าก่อนจ่ายเงิน
- ใช้คูปองตอนสั่งซื้อ และคืนคูปองถ้า Order ไม่สำเร็จ
- ใช้หลายคูปองได้ตามกติกา (Stacking)
- หยุดแจกเมื่อคูปองหมดหรืองบหมด

### Non-Functional Requirement

- **Correctness**: ห้ามแจกเกินจำนวน และห้ามใช้ซ้ำ เพราะทุกใบคือเงินจริง
- **High Concurrency**: รับคนแย่งกดตอน Flash Campaign ได้ (เช่น คูปอง 100,000 ใบ มีคน 1 ล้านคนกดใน 10 วินาที ≈ 100,000 QPS)
- **Low Latency**: คำนวณส่วนลดในตะกร้าได้เร็ว เพราะถูกเรียกทุกครั้งที่ตะกร้าเปลี่ยน
- **Auditability**: ย้อนดูได้ว่าใครใช้คูปองอะไรกับ Order ไหน ได้ส่วนลดเท่าไหร่

## 2. Sketch ภาพระบบคร่าวๆ

ก่อนอื่น มีอยู่ 3 คำที่ต้องแยกให้ออกก่อน
- Campaign: ภาพใหญ่ทางธุรกิจ เช่น "11.11 Mega Sale" ซึ่งมีช่วงเวลา งบรวม และเจ้าของแคมเปญ
- Coupon Template: แม่แบบของคูปอง 1 ประเภทในแคมเปญ เช่น "ลด 100 เมื่อซื้อครบ 500 จำนวน 100,000 ใบ คนละ 1 ใบ"
- Coupon Instance (User Coupon): คูปองแต่ละใบที่อยู่ในมือ User จริงๆ ถูกสร้างตอนกดเก็บหรือกรอก Code แต่ละใบมีสถานะของตัวเอง ไม่ขึ้นกับใบอื่น

![[coupon_campaign_template_instance.png]]

>[!Note] ทำไมต้องแยก Template กับ Instance?
>- Template มีไม่เยอะ กติกาแทบไม่เปลี่ยน แต่ถูกอ่านบ่อยมาก -> Cache ได้ดี
>- Instance มีเยอะมาก และเปลี่ยนสถานะตลอด -> ต้อง Scale อีกแบบ
> 
พอแยกกัน ก็ออกแบบแต่ละฝั่งได้ตรงจุด

### Coupon Lifecycle

คูปอง 1 ใบจะมี 4 สถานะ ก็คือ...
1. **AVAILABLE**: เก็บแล้ว พร้อมใช้
2. **RESERVED**: ถูกจองไว้กับ Order ที่กำลังรอจ่ายเงิน ใช้กับ Order อื่นไม่ได้
3. **USED**: จ่ายเงินสำเร็จ ใช้ไปแล้ว
4. **EXPIRED**: หมดอายุ

![[coupon_life_cycle.png]]

> [!Note] ทำไมต้องมี RESERVED? 
> เพราะตั้งแต่กดสั่งซื้อจนจ่ายเงินสำเร็จมีช่องว่างเวลาอยู่ ถ้าไม่จองคูปองไว้ก่อน User อาจเปิด 2 แท็บ แล้วใช้คูปองใบเดียวกันกับ 2 Order ได้

### High-Level Design

![[coupon_high-level_design.png]]

จากภาพ Component หลักๆ จะมี...
- **Campaign Management Service**: ให้ Admin และร้านค้าสร้าง Campaign กับ Template
- **Coupon Service**: ดูแลการเก็บคูปอง และสถานะของคูปองที่ User มี
- **Promotion Engine**: คำนวณว่าคูปองไหนใช้ได้ และได้ส่วนลดเท่าไหร่ -> เป็น Stateless และอ่านกติกาจาก Cache
- **Order Service / Payment Service**: เรียก Coupon Service ตอนจอง ยืนยันการใช้ และคืนคูปอง
- **Redis**: เก็บ Template ที่ Active อยู่, จำนวนคูปองคงเหลือ และรายชื่อคนที่เก็บไปแล้ว
- **Message Queue**: รับงานเขียน DB แบบ Async ตอน Flash Claim (อ่านเพิ่มเติมได้ใน [[23 Distributed Message Queue|Distributed Message Queue]])
- **Coupon DB**: Source of Truth ของคูปองทั้งหมด

ระบบจะมี 2 Flow ที่มีลักษณะต่างกัน ก็คือ...
1. Coupon Claim Flow
2. Coupon Redeem Flow
เรามาดูทีละ Flow กัน

#### Coupon Claim Flow

![[coupon_claim_flow.png]]

Flow นี้ Write จะพุ่งขึ้นเป็นพักๆ ตอนมี Flash Campaign เลยต้องเน้นรับ Spike ให้ไหว
1. User กดเก็บคูปองผ่าน API Gateway ซึ่งจะทำ Rate Limit ต่อ User ก่อน (อ่านเพิ่มเติมได้ใน [[01 Rate Limiter|Rate Limiter]])
2. Coupon Service เช็ค Template จาก Cache ว่ายังอยู่ในช่วงเวลาเก็บคูปอง และ Campaign ยังไม่ถูกหยุด
3. Coupon Service รัน **Lua Script** ใน Redis เพื่อเช็คว่ายังมีคูปองเหลือ และ User ยังเก็บไม่เกินสิทธิ์ ถ้าผ่านก็ตัดจำนวน แล้วจดไว้ว่า User คนนี้เก็บแล้ว
4. Coupon Service ส่ง Message "สร้าง User Coupon" เข้า Queue แล้วตอบ User ทันทีว่าเก็บสำเร็จ
5. Consumer ดึง Message ไปเขียนลง Coupon DB

#### Coupon Redeem Flow

![[coupon_redeem_flow.png]]

Flow นี้ Write ไม่เยอะเท่า Claim แต่ต้องถูกต้องที่สุด เพราะผูกกับเงินโดยตรง
1. ระหว่างที่ User เลือกของ แอปจะเรียก Preview ให้ Promotion Engine คำนวณส่วนลด และแนะนำคูปองที่คุ้มที่สุด (อ่านอย่างเดียว ไม่จองอะไร)
2. พอ User กดสั่งซื้อ Order Service จะสร้าง Order สถานะ `PENDING_PAYMENT` แล้วขอจองคูปอง
3. Coupon Service ให้ Promotion Engine คำนวณส่วนลดใหม่จาก Cart Snapshot (ห้ามเชื่อตัวเลขจาก Client) แล้วเปลี่ยนคูปองเป็น `RESERVED` ผูกกับ `order_id` และตัดงบแคมเปญ
4. Order Service เรียก Payment Service ให้ User จ่ายเงินตามยอดหลังหักส่วนลด
5. ถ้าจ่ายสำเร็จ -> Order Service สั่งยืนยัน คูปองเปลี่ยนเป็น `USED`
6. ถ้าจ่ายไม่สำเร็จ ยกเลิก หรือหมดเวลา -> Order Service สั่งคืน คูปองกลับเป็น `AVAILABLE` และคืนงบแคมเปญ

### API Design

1. **POST** `/v1/templates/{:templateId}/claim` สำหรับการกดเก็บ Coupon

**Response**

| Field     | Description                    | Type      |
| --------- | ------------------------------ | --------- |
| couponId  | ID ของ Coupon ที่ User เก็บได้ | String    |
| status    | สถานะของ Coupon (AVAILABLE)    | String    |
| expiresAt | วันหมดอายุของ Coupon           | Timestamp |

2. **GET** `/v1/me/coupons?status={:status}` สำหรับการดู Coupon ที่ User มี

**Response**

| Field      | Description                                                 | Type      |
| ---------- | ----------------------------------------------------------- | --------- |
| couponId   | ID ของ Coupon ที่ User เก็บได้                              | String    |
| templateId | Template ของ Coupon นี้                                     | String    |
| title      | ชื่อของ Coupon นี้ เช่น **ลด 100 บาท เมื่อซื้อครบ 500 บาท** | String    |
| status     | สถานะของ Coupon                                             | String    |
| expiresAt  | วันหมดอายุของ Coupon                                        | Timestamp |

3. **POST** `/v1/pricing/preview` สำหรับคำนวณส่วนลดของตะกร้าโดยยังไม่จองคูปอง

**Request Body**

| Field     | Description                            | Type  |
| --------- | -------------------------------------- | ----- |
| items     | สินค้าในตะกร้า [{sku: ..., qty: ....}] | Array |
| couponIds | Coupon ที่ User เลือก                  | Array |

**Response**

| Field     | Description                                     | Type  |
| --------- | ----------------------------------------------- | ----- |
| subtotal  | ยอดก่อนหักส่วนลด                                | Long  |
| discounts | ส่วนลดจาก Coupon แต่ละรายการ (couponId, amount) | Array |
| total     | ยอดที่ต้องจ่ายจริงๆ                             | Long  |

4. **POST** `/v1/coupons/reserve` สำหรับจองคูปองให้ Order ตอน Checkout (Internal API ให้ Order Service เรียก)

**Request Body**

| Field        | Description                                   | Type   |
| ------------ | --------------------------------------------- | ------ |
| orderId      | Order ที่จะใช้คูปอง (ใช้เป็น Idempotency Key) | String |
| userId       | User เจ้าของคูปอง                             | String |
| couponIds    | Coupon ที่ User เลือก                         | Array  |
| cartSnapshot | ราคาสินค้าและค่าส่ง ณ ตอนที่กดสั่งซื้อ        | Object |

**Response**

| Field              | Description                         | Type   |
| ------------------ | ----------------------------------- | ------ |
| status             | ผลการจอง (RESERVED หรือ REJECTED)   | String |
| discountAmount     | ส่วนลดรวมจากทุก Coupon              | Long   |
| discountAllocation | ส่วนลดที่กระจายไปให้สินค้าแต่ละชิ้น | Array  |

5. **POST** `/v1/coupons/confirm` และ **POST** `/v1/coupons/release` สำหรับยืนยันการใช้ หรือคืนคูปอง (Internal API)

**Request Body**

| Field   | Description          | Type   |
| ------- | -------------------- | ------ |
| orderId | Order ที่จองคูปองไว้ | String |
>[!Note] ทำไมเงินถึงเป็นจำนวนเต็ม? 
>เพราะว่า...เงินทุกจำนวนจะเก็บเป็นหน่วยที่เล็กที่สุด (สตางค์) แบบจำนวนเต็ม เช่น `30000` = 300.00 บาท จะได้ไม่มีปัญหาทศนิยมเพี้ยน เหมือนใน [[15 Payment System|Payment System]]

### Data Schema

![[coupon_schema.png]]

- **campaign**: แคมเปญ ซึ่งมีช่วงเวลา, เจ้าของ (แพลตฟอร์มหรือร้านค้า) และงบ (`budget_total`, `budget_used`)
- **coupon_template**: กติกาของคูปองแต่ละประเภท
    - `type`, `value`, `max_discount`: รูปแบบส่วนลด เช่น `PERCENT` 10% สูงสุด 200 บาท
    - `min_spend`, `conditions`: ยอดขั้นต่ำ และเงื่อนไขอื่นๆ เช่น หมวดสินค้า, กลุ่ม User, ช่องทางจ่ายเงิน
    - `stacking_group`: กลุ่มที่ใช้กำหนดว่าใช้ร่วมกับคูปองอื่นได้แค่ไหน เช่น `SHOP` / `PLATFORM` / `SHIPPING`
    - `total_quantity`, `per_user_limit`: จำนวนคูปองทั้งหมด และจำนวนที่ User แต่ละคนเก็บได้
    - `valid_type`: `FIXED_DATE` (หมดอายุพร้อมกันทุกใบ) หรือ `RELATIVE` (ใช้ได้ N วันหลังเก็บ)
- **user_coupon**: คูปองในมือ User มี `status`, `order_id` ที่กำลังจองหรือใช้คูปองอยู่ และ `expires_at` ของใบนั้น
- **coupon_code**: ใช้เฉพาะ Code ไม่ซ้ำที่แจกล่วงหน้า ส่วน Code สาธารณะอย่าง `NEWYEAR100` จะสร้าง `user_coupon` ตอนที่ User กรอก Code เลย
- **redemption_log**: บันทึกทุกการ RESERVE / CONFIRM / RELEASE แบบเพิ่มอย่างเดียว (Append-only) เอาไว้ Audit

## 3. เจาะลึกจุดสำคัญๆ

### 1. Flash Claim: แจก Coupon ยังไงไม่ให้เกิน Quota

สมมติคูปองจาก Template ที่ 1 มี 100,000 ใบ แต่มีคนกดพร้อมกัน 1 ล้านคน 
เราจะ resolve ปัญหานี้ยังไงดี?

#### a. เช็คก่อนแล้วค่อยตัด
```sql
SELECT claimed 
FROM coupon_template 
WHERE template_id = 'T1';
```

ถ้า claimed < `total_quantity` ค่อย run...
```sql
UPDATE coupon_template 
SET claimed = claimed + 1 
WHERE template_id = 'T1';
```

**ปัญหาคือ** อาจจะเกิด Race Condition แบบเดียวกับตอนจองห้องใน [[16 Hotel Reservation System|Hotel Reservation System]] คือ... ถ้ามี 2 Request อ่านได้ `claimed = 99,999` พร้อมกัน ทั้งคู่ก็จะผ่านเงื่อนไข -> แจกออกไป 100,001 ใบ แทนที่จะเป็น 100,000 ใบ

#### b. Conditional Update ใน DB

ก็คือรวมการเช็คกับการตัดไว้ในคำสั่งเดียว
```sql
UPDATE coupon_template
SET claimed = claimed + 1
WHERE template_id = 'T1' 
AND claimed < total_quantity;
-- ถ้า affected rows = 0 แปลว่าคูปองหมดแล้ว
```

วิธีนี้ดีกว่าวิธีแรก เพราะ DB จะล็อคแถวตอน UPDATE
**แต่ปัญหาคือ** ทุก Request จะวิ่งไปล็อคแถวเดียวกันหมด (Hot Row) ถ้า 100,000 QPS เข้าแถวเดียว DB รับไม่ไหวแน่ๆ ก็เลยมีอีกวิธี...

>[!Note] Hot Row คืออะไร?
>Hot Row คือการที่แถวเดียวใน DB ที่มี Request จำนวนมากแย่งกันเขียน เพราะ DB จะล็อคแถวไว้ตอน `UPDATE` ทำให้ทุก Request ต้องต่อคิวรอกันทีละคน ต่อให้เพิ่ม Server เท่าไหร่ก็ไม่ช่วย เพราะคอขวดอยู่ที่แถวเดียวนั้น

#### c. Redis + Lua Script

ย้ายการตัดจำนวนไปทำใน Redis ซึ่งอยู่ใน Memory และทำงานทีละคำสั่ง แล้วใช้ **Lua Script** รวมหลายคำสั่งให้ทำงานแบบ Atomic
```lua
-- KEYS[1] = coupon:stock:{T1}      จำนวนคงเหลือ
-- KEYS[2] = coupon:claimed:{T1}    Hash ว่า User แต่ละคนเก็บ Coupon ไปกี่ใบ
-- ARGV[1] = user_id 
-- ARGV[2] = จำนวน Coupon สูงสุดที่ User 1 คนเก็บได้ (per_user_limit)

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
  return -1   -- Coupon หมดแล้ว
end

local claimed = tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0')
if claimed >= tonumber(ARGV[2]) then
  return -2   -- User เก็บครบสิทธิ์แล้ว
end

redis.call('DECR', KEYS[1])
redis.call('HINCRBY', KEYS[2], ARGV[1], 1)
return 1      -- สำเร็จ
```

> [!Note] ทำไมต้องใช้ Lua? 
> ถ้าเรียก `GET` แล้วค่อย `DECR` แยกกันจาก Application ก็จะเจอ Race Condition แบบวิธี a. อีก แต่ Lua Script จะรันจบทั้งก้อนในทีเดียว ไม่มี Request อื่นแทรกเข้ามากลางทางได้
> 
> ส่วน `{T1}` ใน Key คือ **Hash Tag** ของ Redis Cluster ซึ่งทำให้ Key ที่มีค่าใน `{}` เหมือนกันไปอยู่ Node เดียวกัน เพราะ Lua Script รันข้าม Node ไม่ได้

พอ Redis ตอบว่าสำเร็จ ก็ส่ง Message เข้า Queue แล้วให้ Consumer ค่อยๆ เขียนลง DB ทีหลัง DB จะได้ไม่ต้องรับ Spike ตรงๆ (อ่านเพิ่มเติมได้ใน [[14 Synchronous VS Asynchronous|Synchronous VS Asynchronous]])

แต่ข้อมูลใน Redis กับ DB ก็อาจไม่ตรงกันได้ ซึ่งมี 3 กรณี
- **Redis ตัดจำนวนแล้ว แต่ส่งเข้า Queue ไม่สำเร็จ**: คูปองจะหายไปเฉยๆ แก้ด้วยการ Retry และมี Job กระทบยอดเป็นระยะ ว่าจำนวนที่ Redis ตัดไปตรงกับจำนวน User Coupon ใน DB หรือเปล่า ถ้าไม่ตรงก็คืนจำนวนให้ Redis (แนวคิดเดียวกับ Reconciliation ใน [[15 Payment System|Payment System]])
- **Consumer เขียน DB ซ้ำ**: เพราะ Queue ส่งแบบ At-least Once เลยต้องใส่ Unique Constraint ไว้ เช่น `(template_id, user_id, claim_seq)` เขียนซ้ำก็จะไม่ได้แถวใหม่
- **Redis ล่ม**: Redis ไม่ใช่ Source of Truth พอกลับมาก็สร้างจำนวนคงเหลือใหม่จาก DB ได้

### 2. ป้องกันไม่ให้มี Coupon ถูกใช้ซ้ำ

จะมี 2 กรณีที่ต้องกัน ก็คือ...
1. **Request เดิมถูกส่งซ้ำ**: เช่น Order Service เรียกจองคูปองแล้ว Timeout เลย Retry ใหม่ แบบนี้ต้องได้ผลเหมือนเดิม -> ใช้ `order_id` เป็น **Idempotency Key** ถ้าคูปองถูกจองไว้กับ `order_id` นี้แล้ว ก็ตอบผลเดิมกลับไปเลย
2. **2 Order แย่งใช้คูปองใบเดียวกัน**: เช่น User เปิด 2 แท็บแล้วกดสั่งซื้อพร้อมกัน -> ใช้ **Conditional Update** ในการเปลี่ยนสถานะ
```sql
UPDATE user_coupon
SET status = 'RESERVED', order_id = 'ORD-1', version = version + 1
WHERE coupon_id = 'C001'
  AND user_id = 'U123'
  AND status = 'AVAILABLE'
  AND expires_at > NOW();
-- affected rows = 1  → จองสำเร็จ
-- affected rows = 0  → ถูกใช้ไปแล้ว / หมดอายุ / ไม่ใช่ของ User นี้
```

คำสั่งนี้สามารถเช็คได้ครบว่าคูปองเป็นของ User คนนี้จริง และยังไม่หมดอายุ ส่วน Order ที่มาทีหลังจะได้ `affected rows = 0` เพราะสถานะไม่ใช่ `AVAILABLE` แล้ว ซึ่งก็คือ **Optimistic Locking** ที่ใช้สถานะแทน Version Number นั่นเอง -> prevent กรณีที่ 2 ได้

แต่ถ้าเป็น Retry ที่เข้ามาหลังจองสำเร็จไปแล้ว คำสั่งข้างบนก็จะได้ `affected rows = 0` เหมือนกัน ทั้งที่คูปองถูกจองให้ Order นี้เอง เพราะงั้นถ้าได้ `0` ต้องเช็คต่อว่าคูปองถูกจองไว้กับ Order ไหน
```sql
SELECT status, order_id 
FROM user_coupon 
WHERE coupon_id = 'C001';
-- status = 'RESERVED' และ order_id = 'ORD-1' → Request ซ้ำ ตอบผลเดิมจาก redemption_log
-- อย่างอื่น → ใช้คูปองไม่ได้จริงๆ
```

-> prevent กรณีที่ 1 ได้

ส่วน Code สาธารณะอย่าง `NEWYEAR100` ที่ไม่ได้มี Instance ไว้ล่วงหน้า ก็จะสร้าง User Coupon ตอนกรอก Code แล้วใช้ Unique Constraint `(template_id, user_id)` กันไม่ให้คนเดียวใช้ซ้ำได้

### 3. ระบบจอง Coupon ไปแล้ว User ไม่จ่ายเงิน และการคืนเงิน

#### Reservation Timeout

ถ้า User กดสั่งซื้อแล้วปิดแอปไปเลย คูปองจะค้างอยู่ที่ `RESERVED` ตลอดไป เลยต้องมีกลไกคืนคูปองด้วย
1. Order ที่เป็น `PENDING_PAYMENT` จะมีอายุ เช่น 15 นาที
2. ตอนสร้าง Order ก็ส่ง **Delayed Message** ที่จะไปถึงในอีก 15 นาที พอถึงเวลาก็เช็คว่าจ่ายเงินหรือยัง ถ้ายังก็ยกเลิก Order แล้วสั่งคืนคูปอง
3. เผื่อ Message หาย ก็มี Job คอยสแกนคูปองที่ `RESERVED` นานเกินกำหนดเป็นอีกชั้นนึง

ซึ่งการคืนคูปองก็ต้อง Idempotent และเป็น Conditional Update เหมือนกัน
```sql
UPDATE user_coupon
SET status = 'AVAILABLE', order_id = NULL
WHERE coupon_id = 'C001' 
AND status = 'RESERVED' 
AND order_id = 'ORD-1';
```

เงื่อนไข `order_id = 'ORD-1'` สำคัญมาก เพราะกันไม่ให้คำสั่งคืนที่มาช้าของ Order เก่า ไปปลดคูปองที่ตอนนี้ถูก Order ใหม่จองอยู่

> [!Note] ถ้าจ่ายเงินสำเร็จ แต่คูปองถูกคืนไปแล้วล่ะ? 
> ถ้า User จ่ายเงินตอนวินาทีสุดท้าย แต่ Timeout ทำงานไปก่อน คูปองจะกลับเป็น `AVAILABLE` ทั้งที่เงินเข้ามาแล้ว 
> 
> ทางแก้คือตอนยืนยัน ถ้าคูปองไม่ได้ `RESERVED` อยู่กับ Order นี้แล้ว ก็ให้ลองจองใหม่ ถ้าจองไม่ได้ (เช่น ถูกเอาไปใช้กับ Order อื่นแล้ว) ก็ต้องตัดสินใจทางธุรกิจ เช่น ยอมให้ส่วนลดไป หรือคืนเงินส่วนต่าง แล้วบันทึกไว้ให้ทีมตรวจสอบ

#### การคืนเงินหลังใช้คูปองไปแล้ว

ถ้าคืนทั้ง Order ก็คืนคูปองตามนโยบายของแคมเปญ แต่ถ้า**คืนแค่บางชิ้น** จะคืนเงินเท่าไหร่ดี? ตรงนี้เลยต้องมี **Discount Allocation**

สมมติซื้อสินค้า 2 ชิ้น ราคา 600 กับ 400 บาท แล้วใช้คูปองลด 100 บาท

| สินค้า | ราคา | สัดส่วน | ส่วนลดที่แบ่งให้ | จ่ายจริง |
| ------ | ---- | ------- | ---------------- | -------- |
| A      | 600  | 60%     | 60               | 540      |
| B      | 400  | 40%     | 40               | 360      |

ถ้าคืนสินค้า B ก็คืนเงิน **360** บาท ไม่ใช่ 400 บาท เพราะส่วนลด 40 บาทถูกแบ่งให้สินค้า B ไปแล้ว 
เพราะงั้นตอนจองคูปองต้องคำนวณและบันทึกการแบ่งนี้ไว้ใน `redemption_log` เลย และถ้าแบ่งแล้วมีเศษสตางค์ ก็ปัดให้สินค้าชิ้นสุดท้าย เพื่อให้ผลรวมตรงกับส่วนลดทั้งหมดพอ

### 4. Promotion Engine และการใช้หลาย Coupon

ตรงนี้เป็นจุดที่สำคัญที่สุดละ (ดูจากขนาดความยาวได้เลย)

#### Rule = Condition + Action

ถ้าเขียน `if` ของทุกแคมเปญไว้ใน Code ทุกครั้งที่มีแคมเปญใหม่ก็ต้อง Deploy ใหม่ เราเลยเก็บกติกาไว้เป็น**ข้อมูล**แทน โดยแต่ละ Template จะมี
- **Condition**: เงื่อนไขที่ต้องผ่าน เช่น ยอดขั้นต่ำ, หมวดสินค้า, กลุ่ม User, ช่องทางจ่ายเงิน
- **Action**: ส่วนลดที่จะได้ เช่น ลด 10% สูงสุด 200 บาท

ตัวอย่างเช่น คูปอง "ลด 10% สูงสุด 200 บาท สำหรับสินค้า Fashion และ Beauty ซื้อครบ 500 บาท เฉพาะ User ใหม่ที่จ่ายด้วยบัตร Bank X" ก็จะเขียน conditions และ actions ได้ประมาณนี้
```json
{
	"template_id": "T1",
	"conditions": {
		"user_segments": ["new_user"],
		"categories": ["fashion", "beauty"],
		"min_spend": 50000,
		"payment_methods": ["credit_card_bank_x"]
	},
	"action": {
		"type": "PERCENT",
		"value": 1000,
		"max_discount": 20000
	}
}
```

Note: หน่วยเงินเป็นสตางค์ และเปอร์เซ็นต์เป็น Basis Point -> `50000` = 500 บาท, `1000` = 10%, `20000` = 200 บาท

ทีนี้สมมติ User ใหม่คนหนึ่งมีของในตะกร้าแบบนี้ และเลือกจ่ายด้วยบัตร Bank X

| สินค้า | หมวด       | จำนวน | ราคารวม |
| ------ | ---------- | ----- | ------- |
| SKU-1  | fashion    | 2     | 2000    |
| SKU-2  | beauty     | 1     | 500     |
| SKU-3  | electronic | 1     | 1500    |

Promotion Engine จะทำงานเป็น 2 ขั้น ก็คือ...
1. **เช็ค Condition ทีละข้อ** เรียงจากข้อที่เช็คง่ายไปยาก เจอข้อไหนไม่ผ่านก็หยุดทันที (Short-circuit)

| ลำดับ | Condition       | เช็คกับอะไร                                 | ผล                                      |
| ----- | --------------- | ------------------------------------------- | --------------------------------------- |
| 1     | user_segments   | User เป็น new_user มั้ย                     | ผ่าน                                    |
| 2     | categories      | สินค้าชิ้นไหนอยู่ในหมวดที่ใช้ได้            | ผ่าน -> สินค้าที่ใช้ได้คือ SKU-1, SKU-2 |
| 3     | min_spend       | ยอดของสินค้าที่ใช้ได้ ≥ 500 มั้ย            | ผ่าน -> 2,000 + 500 = 2,500 ≥ 500       |
| 4     | payment_methods | ช่องทางจ่ายเงินที่เลือกเป็นบัตร Bank X มั้ย | ผ่าน                                    |

2. **คำนวณ Action จากสินค้าที่ใช้ได้**

Flow ในการคำนวณส่วนลด ก็จะเป็นประมาณนี้
1. ยอดของสินค้าที่ใช้ได้ = 2,500 บาท
2. `PERCENT` 10% -> 2,500 × 10% = 250 บาท
3. ติดเพดาน `max_discount` -> ส่วนลดจริง = min(250, 200) = **200 บาท**
4. แบ่งส่วนลดให้สินค้าตามสัดส่วน (Discount Allocation): SKU-1 ได้ 160 บาท (80%), SKU-2 ได้ 40 บาท (20%), SKU-3 ไม่ได้ส่วนลด

ผลที่ได้ก็เป็นประมาณนี้
```json
{
	"template_id": "T1",
	"eligible": true,
	"discount_amount": 20000,
	"allocation": [
		{"sku": "SKU-1", "amount": 16000},
		{"sku": "SKU-2", "amount": 4000}
	]
}
```

แต่ถ้าไม่ผ่าน Engine จะตอบเหตุผลกลับไปด้วย แอปจะได้บอก User ถูก เช่น ถ้าเลือกจ่ายด้วยบัตรธนาคารอื่น ก็จะหยุดที่ข้อ 4 แล้วตอบแบบนี้
```json
{
	"template_id": "T1",
	"eligible": false,
	"reason": "PAYMENT_METHOD_NOT_ELIGIBLE"
}
```

> [!Note] ถ้าตอน Preview ยังไม่รู้ว่าจะจ่ายด้วยอะไรล่ะ? 
> ตอน User กำลังเลือกของ ส่วนใหญ่ยังไม่ได้เลือกช่องทางจ่ายเงิน Engine เลยข้าม Condition ข้อนี้ไปก่อน แล้วตอบว่า "ใช้ได้ถ้าจ่ายด้วยบัตร Bank X" แทนการตอบว่าไม่ผ่าน พอ User เลือกบัตรตอนจ่ายเงิน ก็ค่อยเช็คข้อนี้จริงอีกที (ดูต่อได้ในข้อ 7.)

#### Condition ซ้อนกัน (AND / OR)

ตัวอย่างข้างบนทุกเงื่อนไขต้องผ่านหมด (AND) แต่ทีมการตลาดมักอยากได้กติกาที่ซับซ้อนกว่านั้น เช่น คูปอง "ลด 15% สูงสุด 300 บาท" ที่ใช้ได้เมื่อ...
- เป็น User ใหม่ **หรือ** สมาชิก Gold
- **และ** ซื้อ Fashion ครบ 1,000 บาท **หรือ** ซื้อ Beauty ครบ 500 บาท
- **และ** จ่ายด้วยบัตร Bank X

ด้วยเงื่อนไขที่ซับซ้อนขนาดนี้...จะเก็บเป็น Plain JSON ก็คงไม่ไหวแล้ว เลยต้องเก็บเป็น **Tree** ที่มี Node 3 แบบ ก็คือ...
1. **ALL**: Child Node ทุกตัวต้องผ่าน (AND)
2. **ANY**: Child Node ตัวใดตัวหนึ่งผ่านก็พอ (OR)
3. **LEAF**: เงื่อนไขจริงๆ 1 ข้อ ประกอบด้วย `field`, `op` และ `value`
```json
{
	"type": "ALL",
	"children": [
		{
			"type": "ANY",
			"children": [
				{"type": "LEAF", "field": "user_segment", "op": "EQ", "value": "new_user", "children": NULL},
				{"type": "LEAF", "field": "member_tier", "op": "EQ", "value": "GOLD", "children": NULL}
			]
		},
		{
			"type": "ANY",
			"children": [
				{"type": "LEAF", "field": "category_spend.fashion", "op": "GTE", "value": 100000, "children": NULL},
				{"type": "LEAF", "field": "category_spend.beauty", "op": "GTE", "value": 50000, "children": NULL}
			]
		},
		{"type": "LEAF", "field": "payment_method", "op": "EQ", "value": "credit_card_bank_x", "children": NULL}
	]
}
```

ภาพที่ได้ก็เป็นประมาณนี้
```txt
ALL
├── ANY
│   ├── user_segment = new_user
│   └── member_tier = GOLD
├── ANY
│   ├── ยอด fashion ≥ 1,000
│   └── ยอด beauty ≥ 500
└── payment_method = credit_card_bank_x
```

สมมติว่า User เป็นสมาชิกระดับ Gold (ไม่ใช่ User ใหม่) ซื้อ Fashion 800 บาท กับ Beauty 600 บาท และจ่ายด้วยบัตร Bank X

Engine จะไล่เช็คจากบนลงล่าง โดย **ALL หยุดทันทีที่เจอลูกที่ไม่ผ่าน** ส่วน **ANY หยุดทันทีที่เจอลูกที่ผ่าน**

| ลำดับ | Node                    | ผล                                                          |
| ----- | ----------------------- | ----------------------------------------------------------- |
| 1     | user_segment = new_user | ไม่ผ่าน -> ANY ยังไม่จบ ไปเช็คตัวถัดไป                      |
| 2     | member_tier = GOLD      | ผ่าน -> ANY ตัวแรกผ่าน ไม่ต้องเช็คตัวอื่นใน ANY นี้แล้ว     |
| 3     | ยอด fashion ≥ 1,000     | ไม่ผ่าน (800) -> ไปเช็คตัวถัดไป                             |
| 4     | ยอด beauty ≥ 500        | ผ่าน (600) -> ANY ตัวที่สองผ่าน                             |
| 5     | payment_method = Bank X | ผ่าน                                                        |
| 6     | ALL                     | Child Node ผ่านครบทั้ง 3 ตัว (ลำดับ 2, 4, 5) -> คูปองใช้ได้ |

ที่ต้องระวังคือ**สินค้าที่ใช้คูปองได้ขึ้นกับว่าผ่าน Root ไหน** ในตัวอย่างนี้ผ่านเพราะ Beauty อย่างเดียว Fashion ไม่ได้ส่วนนี้ เลยคิดส่วนลดจาก Beauty อย่างเดียว -> 600 × 15% = 90 บาท (ไม่ถึงเพดาน 300) ถ้าผ่านทั้ง 2 กิ่งก็คิดจากสินค้าทั้ง 2 หมวดรวมกัน

ฝั่ง Engine ก็เขียนเป็น Recursive Function สั้นๆ ได้เลย
```txt
evaluate(node, context):
  if node.type == LEAF: return compare(context[node.field], node.op, node.value)
  if node.type == ALL:  for child in node.children: if not evaluate(child) return false; return true
  if node.type == ANY:  for child in node.children: if evaluate(child) return true; return false
```

พอวาง Structure และเก็บ Data แบบนี้ ทีมการตลาดก็ประกอบกติกาใหม่จากหน้า Admin ได้เอง โดยไม่ต้องแก้ Code และไม่ต้อง Deploy ใหม่

#### ลำดับการคำนวณ

ถ้าคิดส่วนลดคนละลำดับ ผลลัพธ์ก็จะต่างกัน เลยต้องกำหนดลำดับไว้ให้ชัด เช่น
1. เริ่มจากราคาสินค้าแต่ละชิ้น แล้วหักส่วนลดระดับสินค้า (เช่น ซื้อ 2 แถม 1)
2. รวมเป็นยอดรวม แล้วหักคูปองร้านค้า
3. หักคูปองแพลตฟอร์ม (คิดจากยอดหลังข้อ 2.)
4. บวกค่าส่ง แล้วหักคูปองส่งฟรี
5. หักส่วนลดตามช่องทางจ่ายเงิน
6. ได้ยอดสุดท้าย พร้อมรายละเอียดว่าแต่ละส่วนลดหักไปเท่าไหร่

#### Stacking

สุดท้ายท้ายสุด แต่ละ Template จะมี `stacking_group` แล้วกำหนดว่าแต่ละกลุ่มใช้ได้กี่ใบ เช่น `SHOP` ได้ 1 ใบต่อร้าน, `PLATFORM` ได้ 1 ใบต่อ Order และ `SHIPPING` ได้ 1 ใบต่อ Order

ถ้า User มีคูปองหลายใบในกลุ่มเดียวกัน แอปมักจะช่วยเลือกให้ ซึ่งทำได้ 3 แบบ
- **Highest Priority**: เลือกใบที่ Priority สูงสุด -> ง่าย คาดเดาได้ แต่อาจไม่ใช่ใบที่คุ้มที่สุด
- **Best Deal ทีละกลุ่ม**: ในแต่ละกลุ่มลองคำนวณทุกใบ แล้วเลือกใบที่ลดได้เยอะสุด -> คุ้มและเร็ว เพราะคูปองในมือ User มักมีไม่เยอะ
- **Best Combination**: ลองทุกชุดผสมข้ามกลุ่ม -> คุ้มที่สุด แต่จำนวนชุดจะโตเร็วมาก

ส่วนใหญ่จะใช้ **Best Deal ทีละกลุ่ม** ไล่ตามลำดับการคำนวณข้างบน เพราะได้ผลดีพอ และเร็วพอสำหรับ Preview ที่ถูกเรียกบ่อยๆ

### 5. คุมงบรวมของ Campaign

แค่จำกัดจำนวนคูปองยังคุมเงินไม่ได้ เช่น คูปองลด 10% สูงสุด 500 บาท จำนวน 10,000 ใบ
- ถ้าทุกคนซื้อแค่ 1,000 บาท -> ลดใบละ 100 บาท รวม 1 ล้านบาท
- ถ้าทุกคนซื้อ 5,000 บาทขึ้นไป -> ลดใบละ 500 บาท รวม 5 ล้านบาท

จำนวนใบเท่ากัน แต่เงินที่เสียไปต่างกันถึง 5 เท่า แคมเปญเลยต้องมี**งบรวม** (`budget_total`) ด้วย
- **ตอนจอง**: ตัดงบตามส่วนลดที่คำนวณได้จริง ถ้างบเหลือไม่พอก็ใช้คูปองนั้นไม่ได้
- **ตอนคืน**: คืนงบกลับเข้า Campaign
```sql
-- จองคูปองที่ได้ส่วนลด 100 บาท (10000 สตางค์)
UPDATE campaign
SET budget_used = budget_used + 10000
WHERE campaign_id = 'CP1' 
AND budget_used + 10000 <= budget_total;
-- affected rows = 0 → งบไม่พอแล้ว
```

**ปัญหาคือ** ทุก Order ที่ใช้คูปองในแคมเปญนี้ ต้องมา UPDATE แถวเดียวกันหมด คือ Campaign Schema แถวที่ campaign_id = `CP1` ก็จะกลายเป็น Hot Row แบบเดียวกับข้อ 1. อีก

ทางแก้คือ**แบ่งงบเป็นก้อน**ให้แต่ละ Instance ของ Coupon Service ถือไว้ เช่น งบ 1 ล้านบาท มี 5 Instance
1. แต่ละ Instance ขอก้อนงบจาก DB ทีละ 10,000 บาท (ใช้ Conditional Update ข้างบน แต่ตัดทีละ 10,000)
2. พอมี Order เข้ามา ก็ตัดงบจากก้อนใน Memory ของตัวเองเลย ไม่ต้องไปแตะ DB
3. ก้อนหมดเมื่อไหร่ ค่อยไปขอก้อนใหม่

ถ้าส่วนลดเฉลี่ย Order ละ 100 บาท ก้อนละ 10,000 บาทจะใช้ได้ประมาณ 100 Order -> DB โดนเรียกแค่ 1 ครั้งต่อ 100 Order แทนที่จะเป็นทุก Order และงบก็**ไม่มีทางเกิน** เพราะทุกก้อนถูกหักออกจาก DB ไปแล้วตั้งแต่ตอนขอ แต่ก็แลกกับการที่**งบอาจค้าง**อยู่ในบาง Instance เช่น งบใน DB หมดแล้ว แต่ Instance A ยังเหลือ 8,000 บาทที่ไม่มีใครใช้ Order ที่วิ่งไป Instance อื่นจึงโดนตอบว่างบหมด เลยต้องมี...
- **คืนก้อนที่เหลือ**: ตอน Instance ปิดตัว หรือไม่ได้ใช้ก้อนนั้นนานเกินกำหนด
- **ลดขนาดก้อนตอนใกล้หมด**: เช่น งบเหลือไม่ถึง 10% ก็ขอทีละ 1,000 บาทแทน
- **Alert**: แจ้งเตือนตอนใช้งบไป 80% และ 90% ให้ทีมการตลาดตัดสินใจว่าจะเติมงบหรือปล่อยให้หมด

### 6. ส่วนลดตามบัตร

Promotion อย่าง "จ่ายด้วยบัตรเครดิต Bank X ลด 10% สูงสุด 300 บาท" เจอบ่อยมาก แต่ทำยากกว่า Coupon ทั่วไป เพราะ**ส่วนลดขึ้นกับบัตร แต่ระบบจะรู้ว่าเป็นบัตรอะไรก็ตอนถึงขั้นจ่ายเงินแล้ว** และต้องรู้ให้ได้ก่อนตัดเงินจริง

ซึ่งโปรบัตรจะมี 2 แบบหลักๆ ก็คือ...
1. **Instant Discount**: หักส่วนลดตอนจ่ายเลย User จ่ายแค่ยอดหลังหักส่วนลด -> ระบบเราต้องคำนวณส่วนลดเอง
2. **Cashback**: User จ่ายเต็มราคา แล้วธนาคารค่อยคืนเงินเข้าบัตรทีหลัง -> ระบบเราแค่บันทึกว่า Order นี้เข้าโปร แล้วส่งรายการให้ธนาคาร

เพราะงั้นเราจะมา Discuss แบบที่ยากคือ Instant Discount เพราะต้องรู้ว่าเป็นบัตรอะไรก่อนตัดเงิน เดี๋ยวเรามาดูกันว่าทำยังไง

#### รู้ได้ยังไงว่าเป็นบัตรอะไร?

![[coupon_bin.png]]

เลข 6–8 หลักแรกของบัตรเรียกว่า **BIN (Bank Identification Number)** ซึ่งบอกได้ว่าธนาคารไหนออกบัตร (Issuer), เป็น Network อะไร (Visa, Mastercard, JCB), เป็น Credit หรือ Debit และเป็นบัตรระดับไหน

**ปัญหาคือ** ตาม **PCI DSS** ระบบเราห้ามรับหรือเก็บเลขบัตรเต็มเอง (อ่านเพิ่มเติมได้ใน [[15 Payment System|Payment System]]) เลยต้องให้ User กรอกบัตรในหน้าหรือ SDK ของ **PSP (Payment Service Provider)** แทน แล้ว PSP จะส่งกลับมาให้เรา 2 อย่าง ก็คือ...
- **Token**: ค่าที่ใช้แทนบัตรใบนั้นตอนสั่งตัดเงิน
- **ข้อมูลที่ไม่ใช่ความลับ**: เช่น BIN, เลข 4 ตัวท้าย และ **Card Fingerprint** (บัตรใบเดิมได้ค่าเดิมเสมอ ไม่ว่าจะผูกกับบัญชีไหน)

พอได้ BIN มาแล้ว ก็เอาไปเทียบกับเงื่อนไขของโปร ซึ่งเก็บไว้ในตาราง `coupon_scope` แบบ `scope_type = 'BIN'` (ดูในหัวข้อเทคนิคการออกแบบ Schema) โดยต้องลองเทียบตั้งแต่ BIN 8 หลักลงไปจนถึง 6 หลัก เพราะบัตรรุ่นใหม่ใช้ BIN 8 หลัก ขณะที่บัตรรุ่นเก่ายังเป็น 6 หลัก
```sql
-- บัตรเลขขึ้นต้นด้วย 45678912...
SELECT template_id
FROM coupon_scope
WHERE scope_type = 'BIN'
  AND scope_value IN ('45678912', '4567891', '456789');
```

ที่ใช้ `IN` ได้เพราะเป็นการเทียบกับค่าตรงๆ -> ใช้ Index ของ `(scope_type, scope_value)` ได้

#### Instant Discount Flow
![[coupon_instant_discount_bin.png]]

1. User มาถึงหน้าจ่ายเงิน แล้วเลือกหรือกรอกบัตร
2. SDK ของ PSP ส่งข้อมูลบัตรไปที่ PSP โดยตรง แล้วได้ Token พร้อม BIN กลับมา
3. Client ส่ง Token ให้ Order Service จากนั้น Order Service ส่ง BIN และ Fingerprint ต่อให้ Promotion Engine
4. Promotion Engine เจอโปรที่ตรงกับ BIN ก็คำนวณส่วนลด แล้วแอปก็แสดงยอดใหม่ให้ User เห็นก่อนกดยืนยัน
5. พอ User กดยืนยัน Order Service ก็จองโปรเหมือนตอนจองคูปอง และ**ผูกโปรไว้กับ Token ของบัตรใบนี้**
6. Order Service สั่ง PSP ให้**กันวงเงิน (Authorize)** ตามยอดหลังหักส่วนลด โดยให้ใช้ Token นี้เท่านั้น
7. พอได้ผลการกันวงเงินกลับมา ก็เช็คซ้ำอีกรอบว่า BIN ของบัตรที่ถูกกันวงเงินจริงตรงกับโปรหรือเปล่า
    - ถ้าตรง -> สั่ง**ตัดเงินจริง (Capture)** แล้วยืนยันการใช้โปร
    - ถ้าไม่ตรง -> **ยกเลิกการกันวงเงิน (Void)** แล้วคืนสิทธิ์โปร ให้ User จ่ายใหม่ด้วยราคาเต็ม

> [!Note] ทำไมต้องแยก Authorize กับ Capture? 
> ถ้าตัดเงินไปเลยในขั้นที่ 6 แล้วเพิ่งมารู้ว่าบัตรไม่ตรงโปร เงินที่ถูกตัดไปก็เป็นยอดที่หักส่วนลดแล้ว จะไปเรียกเก็บส่วนต่างทีหลังก็ยาก การกันวงเงินไว้ก่อนแล้วค่อยตัดจริง ทำให้ยังยกเลิกได้โดยที่เงินยังไม่ได้ออกจากบัญชี User

> [!Note] ทำไมต้องผูกกับ Token และเช็คซ้ำ? 
> เพื่อกันไม่ให้ User ได้ส่วนลดจากบัตร Bank X แล้วแอบเปลี่ยนไปใช้บัตรอื่นตอนจ่ายจริง เพราะงั้นถ้า User เปลี่ยนบัตร ก็ต้องคำนวณส่วนลดใหม่ทุกครั้ง ซึ่ง PSP บางเจ้าก็มีให้เลือกเลยว่าถ้าบัตรไม่ตรงกับโปร จะ**บล็อกการจ่าย** หรือ**ให้จ่ายเต็มราคา**แทน

#### สิทธิ์ต่อบัตร ไม่ใช่ต่อบัญชี

โปรบัตรมักจำกัดสิทธิ์ เช่น "1 สิทธิ์ต่อบัตรต่อเดือน" ซึ่งจะนับตาม User ไม่ได้ เพราะคนเดียวอาจผูกบัตรใบเดียวกันไว้หลายบัญชี เลยต้องใช้ **Card Fingerprint** เป็น Key ในการนับสิทธิ์แทน แล้วตัดสิทธิ์ด้วย Conditional Update แบบเดียวกับคูปอง
```txt
card_offer_usage(offer_id, card_fingerprint, period, used_count)
PRIMARY KEY (offer_id, card_fingerprint, period)
```

#### บันทึกว่าใครออกเงิน

ส่วนลดจากโปรบัตรไม่จำเป็นต้องเป็นเงินของเราทั้งหมด หลายครั้งธนาคารกับแพลตฟอร์มก็หารกัน (Co-funded) เช่น ส่วนลด 300 บาท ธนาคารออก 70% แพลตฟอร์มออก 30% เพราะงั้นใน `redemption_log` ต้องเก็บให้ชัดว่าส่วนลดก้อนนี้ใครออกไปเท่าไหร่ สิ้นเดือนจะได้รวมยอดส่วนที่ธนาคารออกไปเรียกเก็บ และกระทบยอดกับรายงานของธนาคารได้
```swagger
{
	"order_id": "ORD-1",
	"offer_id": "BANKX-10OFF",
	"discount_amount": 30000,
	"funding": [
		{"party": "BANK_X", "amount": 21000},
		{"party": "PLATFORM", "amount": 9000}
	]
}
```

ส่วนตอนคืนเงิน
- **Instant Discount**: คืนเท่าที่ User จ่ายจริงตาม Discount Allocation และคืนสิทธิ์ต่อบัตรถ้านโยบายอนุญาต
- **Cashback**: ต้องแจ้งธนาคาร ให้ยกเลิกหรือดึง Cashback คืน

### 7. Prevent Code Guessing

#### Bulk Code Generation

Code ที่แจกให้แต่ละคน (เช่น พิมพ์บนใบเสร็จ หรือส่งทาง SMS) ต้อง**เดาไม่ได้** เพราะคนควรได้ Code จากช่องทางที่เราแจกเท่านั้น หรือได้ต่อจากคนที่ได้รับมา ไม่ใช่นั่งสุ่มจนเจอ Code ที่เราไม่ได้ตั้งใจให้ ซึ่งการสร้าง Code จะมี 5 เรื่องที่ต้องคิด ก็คือ...
1. ตัวสุ่ม
2. ตัวอักษรที่ใช้
3. ความยาว
4. Check Digit
5. การ Insert และการเช็ค Code

**1. ตัวสุ่ม**
- **ห้ามใช้เลขเรียง**: เช่น `SALE0001`, `SALE0002` ใครได้ 1 ใบก็เดาใบถัดไปได้ทันที
- **ห้ามใช้ `Math.random()`**: เพราะเป็นตัวสุ่มแบบคำนวณได้ (Pseudo-random) ถ้าเห็นผลลัพธ์ติดกันมากพอ ก็ย้อนหาค่าเริ่มต้น แล้วเดา Code ถัดไปได้
- **ใช้ CSPRNG (Cryptographically Secure Pseudo-Random Number Generator)**: ตัวสุ่มที่ออกแบบมาให้ทำนายไม่ได้ เช่น `crypto.randomInt()` ใน Node.js, `secrets` ใน Python หรือ `SecureRandom` ใน Java

**2. ตัวอักษรที่ใช้**
ถ้าใช้ `A-Z` กับ `0-9` ครบ 36 ตัว จะมีตัวที่หน้าตาคล้ายกันจน User พิมพ์ผิดบ่อย เช่น `0` กับ `O` หรือ `1`, `I` และ `L` เลยตัดออก เหลือประมาณ 30 ตัว
```txt
23456789ABCDEFGHJKMNPQRSTUVWXYZ
```

และแบ่ง Code เป็นกลุ่มให้อ่านง่าย เช่น `K7QX-M2PA-9D` ส่วนตอนเช็คก็ตัด `-` กับช่องว่างทิ้งก่อน

**3. ความยาว**
โอกาสที่สุ่มแล้วเจอ Code จริง = จำนวน Code ที่แจก ÷ จำนวน Code ที่เป็นไปได้ทั้งหมด
ถ้าใช้ 10 ตัวอักษรจาก 30 ตัว จะได้ 30^10 ≈ 5.9 × 10^14 แบบ แล้วแจกไป 1 Million Codes
- สุ่ม 1 ครั้ง มีโอกาสเจอประมาณ 1 ใน 590 ล้าน
- ถ้ามี Rate Limit ให้กรอกผิดได้ 5 ครั้งต่อ 15 นาที -> 1 บัญชีลองได้สูงสุด 480 ครั้งต่อวัน -> โอกาสเจอประมาณ 1 ใน 1.2 ล้านต่อวัน

เพราะงั้นความยาวต้องคิดคู่กับ Rate Limit เสมอ ถ้า Code สั้นกว่านี้ หรือแจกเยอะกว่านี้ ก็ต้องเพิ่มความยาว

**4. Check Digit**
ให้ตัวอักษรตัวสุดท้ายคำนวณมาจากตัวอื่นๆ (เช่น ใช้ Luhn mod N หรือ Damm Algorithm) ทำให้...
- **รู้ได้ทันทีว่าพิมพ์ผิด**: ถ้าพิมพ์ผิด 1 ตัว หรือสลับตัวติดกัน Check Digit จะไม่ตรง ตอบ User ได้เลยว่า "Code ไม่ถูกต้อง" โดยไม่ต้องไปถาม DB
- **ลด Load ของ DB**: Code ที่สุ่มมั่วๆ ส่วนใหญ่จะตกตั้งแต่ขั้นนี้

> [!Note] Check Digit ไม่ได้ช่วยเรื่องความปลอดภัย 
> Algorithm ของ Check Digit เป็นที่รู้กันทั่วไป คนที่สุ่ม Code ก็คำนวณ Check Digit ให้ถูกได้เหมือนกัน แถมตัวอักษร 1 ตัวที่ใช้เป็น Check Digit ก็ไม่ได้สุ่มแล้ว ถ้าอยากให้เดายากเท่าเดิม ก็ต้องเพิ่มความยาวอีก 1 ตัว (รวมเป็น 11 ตัว)

**5. การ Insert และการเช็ค Code**
- **Insert เป็น Batch**: สร้างทีละ 10,000 Codes แล้ว Insert ครั้งเดียว โดยมี Unique Constraint ที่ `code` แล้วใช้ `ON CONFLICT DO NOTHING` ถ้ามี Code ชนก็นับว่าขาดไปกี่ตัว แล้วสุ่มเพิ่มให้ครบ
- **ทำ Code ให้อยู่ในรูปเดียวกัน (Normalize)**: เก็บเป็นตัวพิมพ์ใหญ่ และตอน User กรอก ก็แปลงเป็นตัวพิมพ์ใหญ่ แล้วตัด `-` กับช่องว่างออกก่อนเช็คทุกครั้ง
- **เก็บเป็น Hash ถ้า Code มีมูลค่าสูง**: เช่น Gift Card ถ้า DB หลุด คนก็เอา Code ไปใช้ได้ทันที เลยเก็บเป็น HMAC-SHA256 ของ Code (Hash ที่ต้องใช้ Secret Key) แทนตัว Code จริง ที่ไม่ใช้ bcrypt แบบเก็บ Password (อ่านเพิ่มเติมได้ใน [[03 Password Security|Password Security]]) เพราะ bcrypt ได้ผลไม่เหมือนเดิมทุกครั้ง จะเอา Code ที่ User กรอกไปหาใน DB ไม่ได้
