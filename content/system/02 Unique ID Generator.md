ID หรือว่า Identifier คือสิ่งที่ไว้ใช้แยก 2 ข้อมูลว่ามีความแตกต่างกันนะ ถึง Field อื่นๆ จะเหมือนกันก็ตาม แต่ถ้า ID ต่างกัน แปลว่า 2 ข้อมูลนี้คือข้อมูลคนละตัวกัน 

ถ้าระบบของเรามีเพียง Server เดียว ก็ทำได้ไม่ยากมากหรอกกับการสร้าง ID ให้มีความต่างกัน เพราะสามารถ Auto-Increment ID ของข้อมูลขึ้นไปได้ เช่น Record ที่ 1 มี ID = 1, Record ที่ 2 มี ID = 2 งี้ เป็นต้น

แต่พอเป็น Distributed System หรือว่าระบบที่มี Server หลายตัว มันจะทำงี้ตรงๆ ไม่ได้ละ เพราะจะกลายเป็นว่ามีโอกาสที่ ID ที่กำหนดโดย Server A จะไปตรงกับ ID ที่กำหนดโดย Server B แล้วเสียความเป็น ID ไป ไหนยังจะมีเรื่อง Delay ที่มีผลทำให้การกำหนด ID ใน Server หนึ่งๆ ทำได้ช้าลงอีก แล้วเราจะจัดการกับปัญหานี้ยังไงดี...

---

## 1. ถามรายละเอียดของ Scope งาน

Q1: ID ที่อยากได้จะมีลักษณะยังไงบ้าง
A1: ID จะต้องมีความแตกต่างกันในทุก Record ละก็สามารถเรียงลำดับข้อมูลด้วย ID ได้

Q2: ID จำเป็นต้องเพิ่มทีละ 1 มั้ย
A2: ID มันต้องเปลี่ยนแปลงไปได้ แต่ไม่จำเป็นต้องเพิ่มทีละ 1 -> ID ที่สร้างมาทีหลังควรจะมีค่ามากกว่า ID ที่สร้างขึ้นมาก่อน

Q3: ID จำเป็นต้องเป็นตัวเลขมั้ย
A3: จำเป็นครับ

Q4: ID ควรมีความยาวขนาดไหน
A4: ด้วยงบที่มี ด้วยการใช้งาน เอาเป็น 64 bit ละกัน

Q5: ระบบนี้มันใหญ่ขนาดไหนอ่ะ
A5: มันจะมีการสร้างข้อมูลใหม่ประมาณ 10000 Records ต่อวินาทีเลยอ่ะ

จากเท่าที่คุยๆ กันมา เราจะได้ว่าระบบการสร้าง ID จะเป็นประมาณนี้
- ID จะต้องมีความแตกต่างกันในแต่ละ Record
- ID จะต้องเป็นตัวเลขเท่านั้น
- ID จะต้องเป็น 64-bit
- ระบบสามารถสร้าง ID ใหม่ได้อย่างน้อยๆ 10000 ID ต่อวินาที

## 2. Sketch ภาพระบบคร่าวๆ

มันมีระบบการสร้าง ID ได้หลายแบบอ่ะนะ แล้วแต่ความเหมาะสม ที่จะนำมาพิจารณาจะมีระบบดังต่อไปนี้
- Multi-Master Replication
- Universally Unique Identifier
- Ticket Server
- Twitter Snowflake Approach

### Multi-Master Replication

![[multi_master_replication.png]]

ระบบนี้ตรงตัวนะ คือเรา check ว่าเรามี Server กี่ตัว เวลาที่แต่ละ Server จะสร้างข้อมูลใหม่ ให้เพิ่ม ID ไปอีก n เมื่อ n คือจำนวน Server ที่มี

ยกตัวอย่างเช่น เรามี Server 2 ตัว Server ที่ 1 เริ่มต้น ID = 1, Server ที่ 2 เริ่มต้น ID = 2 จากนั้นถ้าจะต้่องใช้ ID ค่าใหม่ ก็จะให้เพิ่มค่า ID จากที่ใช้ล่าสุดไป 2 หรือจะได้ว่า
- Server ที่ 1 ใช้ ID = 1, 3, 5, ...
- Server ที่ 2 ใช้ ID = 2, 4, 6, ...

ทำให้ตอบโจทย์กับการใช้ ID ที่ไม่ซ้ำกันได้ แต่ว่าก็มีข้อเสียอยู่ คือ
1. การเพิ่ม/ลด Server จะทำได้ยาก เพราะต้องจัดการ ID ใหม่ 
2. แต่ละ Server อาจจะอยู่กันคนละ Timezone กัน ทำให้การใช้ระบบ ID แบบนี้ยังไม่สามารถรับประกัน ลำดับของ ID ตามเวลาที่สร้างข้อมูลได้

### Universally Unique Identifier (UUID)

UUID เป็นตัวเลข 128-bit ที่สร้างขึ้นโดยอิงข้อมูลจาก Server ที่สร้างข้อมูล มีโอกาสที่ UUID จะมีค่าชนกันในแต่ละ Record ต่ำมาก ขนาดที่ว่า "หากสร้าง Record ทุกวินาที จะต้องใช้เวลาอย่างน้อย 1 ปีที่จะทำให้มีโอกาส 50% ที่จะเจอข้อมูลที่มี UUID ตรงกัน..."

>[!Note] ตรงนี้ถือว่าเสริมเรื่อง UUID ละกัน (ไม่ได้ใช้ในระบบนี้)
>![[uuid_v7_structure.png]]
>
>UUID V7 ซึ่งเป็น Version ปัจจุบันจะมี 128 bits ประกอบด้วย...
> - 48 bits Timestamp → บอกเวลาที่สร้าง UUID
> - 4 bits UUID Version → ในภาพคือ `7` หมายถึง UUID v7
> - 12 random bits → สุ่มเพิ่มความ unique
> - 2 bits Variant → บอก format ของ UUID
> - 2 random bits → เพิ่มความ unique
> - 60 random bits → สุ่มเพิ่มความ unique

แน่นอนว่าข้อดีของมันชัดเจนอยู่ละว่ามันจะไม่ซ้ำกัน ต่อให้จะมีการเพิ่ม/ลด Server ก็ไม่ซ้ำกัน แต่ว่าก็มีข้อเสียอ่ะนะ แต่ว่าข้อเสียก็ชัดๆ อยู่เหมือนกัน
1. มันใช้ 128 bit แต่ระบบเราไหวแค่ 64 bit
2. มันไม่ได้เป็น numeric ทุกตัว

### Ticket Server

![[ticket_server_design.png]]

Ticket Server จะคล้ายๆ กับ Multi Master Replication แต่ว่าคนที่กำหนด ID จะมีแค่ตัวเดียว คือ Ticket Server แล้วแจกจ่าย ID ให้กับ Web Server แทน (Web Server ไม่ได้สร้าง ID ใช้เอง) เพราะงั้นถึงจะมี Server หลายตัวก็จะไม่ใช่ปัญหาแต่อย่างใด แต่ว่าก็จะมีข้อเสียใหม่ตามมา คือ
1. มี Single Point of Failure อยู่ที่ตัว Ticket Server เอง ที่ถ้าล่ม การสร้าง ID ก็จะล่มตาม ซึ่งทำให้สร้างข้อมูลใดๆ ไม่ได้เลย
2. ถ้ามี Ticket Server หลายตัวเพื่อแก้ปัญหานี้ ก็จะกลับไปเจอปัญหาเรื่อง **การจัดการ ID ระหว่าง Server** แบบ Multi-Master Replication และระบบจะซับซ้อนขึ้น

### Twitter Snowflake Approach

![[twitter_snowflake_diagram.png]]

Twitter Snowflake คือ การใช้ระบบการสร้าง ID ของ Twitter ที่เรียกว่า Snowflake (ช่างแม่งเหอะ)

ID จะมี 64 bit แบ่งออกเป็น 5 ส่วน
- **Sign bit จำนวน 1 bit** → เป็น bit สำหรับบอกว่าเลขนี้เป็นบวกหรือเป็นลบ (เราจะใช้บวกเป็นหลัก คือ `0`)
- **Timestamp จำนวน 41 bits** → เป็นเวลาที่สร้าง ID โดยนับเป็นหน่วย **milliseconds** จากเวลาเริ่มต้น (epoch) ที่กำหนดไว้
- **Data Center ID จำนวน 5 bits** → ใช้ระบุว่า ID ถูกสร้างจาก Data Center ไหน
- **Machine ID จำนวน 5 bits** → ใช้ระบุว่า ID ถูกสร้างจาก Machine ไหนภายใน Data Center
- **Sequence Number จำนวน 12 bits** → ใช้แยก ID ที่ถูกสร้างภายใน millisecond เดียวกัน (Reset ค่าเป็น 0 ทุกๆ Milliseconds)

ซึ่งระบบนี้ตอบโจทย์ทุกความต้องการ เพราะว่า
1. **ID ไม่ซ้ำกัน** → แต่ละ Data Center และ Machine มี ID ของตัวเอง และ Sequence Number ช่วยแยก ID ที่สร้างใน millisecond เดียวกัน
2. **ID เป็นตัวเลข** → สามารถเก็บเป็น `64-bit Integer` ได้
3. **ID เรียงตามเวลาที่สร้าง** → Timestamp อยู่ด้านหน้าของ ID ทำให้ ID ที่สร้างทีหลังมีค่ามากกว่า ID ที่สร้างก่อนหน้า
4. **รองรับจำนวน ID สูง** → Sequence Number 12 bits ทำให้สามารถสร้างได้สูงสุด `2^12 = 4,096 IDs` ต่อ millisecond หรือประมาณ **4.096 ล้าน IDs/วินาทีต่อ Machine**
5. **รองรับหลาย Server** → ใช้ Data Center ID และ Machine ID แยก Server แต่ละตัว ทำให้หลาย Server สามารถสร้าง ID พร้อมกันได้โดยไม่ชนกัน

## 3. เจาะลึกจุดสำคัญๆ

ด้วยความที่ Twitter Snowflake ตอบโจทย์ที่กำหนดทั้งหมด เราก็จะลงลึกระบบนี้กันต่อ

![[twitter_snowflake_diagram_timestamp.png]]

จุดที่สำคัญที่สุดก็จะอยู่ที่ Timestamp แหละว่าเราจะแปลง Timestamp ออกมาเป็น Milliseconds ได้ยังไง ละทำไมมันถึงตอบโจทย์

สำหรับการแปลง Timestamp มาเป็น Milliseconds นั้น ทำได้โดยเอา เวลาปัจจุบันลบด้วยเวลาเริ่มต้น (Epoch) แล้วแปลงผลลัพธ์ให้อยู่ในหน่วย milliseconds ละก็ทำเป็นเลข 41 bits

ละถ้าจะแปลงค่าใน ID กลับมาเป็น Timestamp ก็ทำเลขในฐาน 2 เป็นเลขฐาน 10 ละเพิ่มด้วยค่าเริ่มต้น จากนั้นก็แปลงกลับเป็น Timestamp

ส่วนสาเหตุที่มันตอบโจทย์ 
1. การใช้ 41 bits มันสามารถให้ค่าได้สูงสุด คือ 2^41 - 1 = 2199023255551 milliseconds หรือประมาณ 69 ปี เท่ากับว่า กว่า ID ระบบนี้จะพัง เพราะ Overflow ก็ต้องผ่านไป 69 ปีนู่น 
2. การใช้ 12 bits สำหรับ Sequence Number ทำให้มีค่าได้ `2^12 = 4,096` แบบ หรือก็คือ Machine หนึ่งตัวสามารถสร้าง ID ได้สูงสุด **4,096 ID ภายใน 1 millisecond** โดย Sequence Number จะถูก Reset เป็น `0` เมื่อเข้าสู่ millisecond ใหม่
