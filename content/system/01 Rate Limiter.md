Rate Limiter ก็ตามชื่อแหละ มันคือตัวจำกัดจำนวนครั้งของการส่ง Request ต่อวินาทีของ User เพื่อป้องกันไม่ให้ User คนนึง spam การส่ง Request มากจนเกินไป (มากจน Server ล่มได้เลยถ้าไม่ได้จำกัดไว้) อ่ะ นับว่าเป็นเครื่องมือที่จำเป็นต้องมีตัวนึงเลยสำหรับการออกแบบ

ทีนี้ เราจะสร้าง Rate Limiter ขึ้นมายังไงได้บ้าง เราจะเอา Framework มาใช้กัน

## 1. ถามรายละเอียดของ Scope งาน

Q1: Rate Limiter อันนี้จะเช็คยังไงว่า API นี้ส่งมาจากคนเดียวกัน? -> IP Address ที่ส่งมา, User ID ที่ส่งมา หรือใช้ Field ไหนครับ
A1: ควรเช็คได้หลายแบบนะ ตอนนี้ยังไม่ตายตัวอ่ะ

Q2: ต้องทำ Scaling มั้ยครับ แบบว่า...ตอนนี้มี User ใช้งานระบบเยอะมั้ยครับ
A2: ถ้าจะทำทั้งที่ ทำให้มันสามารถรับ Request ได้มากๆ เลยละกัน

Q3: ระบบตอนนี้เป็น Distributed รึเปล่าครับ
A3: ใช่ๆ

> [!Note] Distributed System คือระบบที่มีการทำงานร่วมกันของ Server หลายๆ ตัว แต่ผู้ใช้งานจะเห็นเสมือนว่าระบบนี้มี Server ตัวเดียว

Q4: Rate Limiter อันนี้ควรทำเป็น Service ใหม่แยกออกมา หรือเอาไปเป็นส่วนนึงใน Service ที่มีอ่ะครับ
A4: ได้หมดเลย

Q5: ถ้าถึง Limit ของ User แล้ว ต้องมีการแจ้งเตือนกลับไปมั้ยครับ
A5: ต้องมีนะ

โดยสรุปแล้ว...Rate Limiter ที่ดี ควรจะ...
1. จำกัดจำนวนครั้งต่อวินาทีในการส่ง Request ได้อย่างแม่นยำ
2. ต้องไม่เพิ่ม Latency: ไม่เพิ่มเวลาที่ใช้ในการส่ง Request จาก Client ไปหา Server
3. ใช้ Memory น้อย
4. ต้องแสดง Message หรือ Response ว่าถึง Limit แล้วอย่างชัดเจน
5. ถ้า Rate Limiter มีปัญหา ต้องไม่ทำให้ระบบล่ม
6. Rate Limiter ยังต้องสามารถทำงานได้ถูกต้อง แม้ Request ถูกส่งไปยังหลายๆ Server ก็ตาม

### Token Bucket Algorithm
เป็น Algorithm ยอดนิยมเลยสำหรับการทำ Rate Limiter โดยจะเป็นภาพประมาณว่า...

![[token_bucket_algorithm.png]]

ใน Bucket จะมี Token อยู่จำนวนนึง
- ถ้ามี Request เข้ามาแล้วยังมี Token เหลืออยู่ ก็จะอนุญาตให้ Request นั้นผ่านไปได้ แล้วเอา 1 Token ออกจาก Bucket 
- ถ้า Request ที่เข้ามาแล้วไม่มี Token เหลือแล้ว ก็จะไม่ให้ Request นั้น

และเมื่อถึงเวลาที่กำหนดก็จะมีการเติม Token กลับเข้ามาในถัง

แล้วมีเงื่อนไขการสร้างยังไง...
- ต้องกำหนดจำนวน Token ที่ Bucket สามารถรับได้ + ต้องกำหนดจำนวน Token ที่จะเติมเข้า Bucket ในแต่ละวินาที เช่น 2 Request
- ถ้าต้องการให้ 1 User มี Rate Limit --> เมื่อมี User ใหม่ในระบบ ก็สร้าง Bucket สำหรับ User นั้นขึ้นมา
- ถ้าต้องการให้ทุก User มี Rate Limit ร่วมกัน --> ใช้ Bucket เดียวเพื่อครอบคลุมการใช้งานระบบนั้นได้
#### ข้อดี
1. ประหยัด Memory
2. สามารถปรับค่าให้ใช้งานในช่วง Peak ที่มีผู้ใช้งานในระบบเยอะๆ ได้
#### ข้อเสีย
1. ต้องมีการปรับค่าให้เหมาะสมกับการใช้งานอยู่ตลอด

### Sliding Window Algorithm
เป็นอีก Algorithm ที่ได้รับความนิยมสำหรับการทำ **Rate Limiter** โดยแนวคิดคือ **นับจำนวน Request ที่เกิดขึ้นภายในช่วงเวลานึง (Window)** แล้วตรวจสอบว่ายังไม่เกินจำนวนที่กำหนดหรือไม่

ตัวอย่างเช่น กำหนดว่า **อนุญาตได้ 2 Request ภายใน 60 วินาที**

- เมื่อมี Request เข้ามา จะบันทึกเวลาของ Request นั้นไว้
- ก่อนตรวจสอบ จะลบ Request ที่อยู่นอกช่วงเวลา 60 วินาทีออกก่อน
- ถ้าจำนวน Request ที่เหลืออยู่ใน Window ยังไม่เกิน 2 Request ก็จะอนุญาตให้ Request ผ่าน และบันทึกเวลาของ Request ใหม่เข้าไป
- แต่ถ้าภายใน Window มี Request ครบ 2 ครั้งแล้ว ก็จะปฏิเสธ Request นั้นจนกว่าจะมี Request เก่าหลุดออกจากช่วงเวลา

เผื่องง อ่ะ ภาพประกอบ
![[sliding_window_algorithm.png]]

**อนุญาตได้ 2 Request ภายใน 1 นาที**
1. ในเวลา 1:00:01 มี Request A เข้ามา ให้ clear request ทั้งหมดในช่วง 00:00:00 - 00:59:01 ออกไป แล้วก็จดเวลานี้เอาไว้ และด้วยความที่ว่าจำนวน Request ที่จดไว้มี 1 ตัว ยังไม่เกิน 2 ก็อนุญาตให้ Request A ผ่านไปได้
2. ในเวลา 1:00:30 มี Request B เข้ามา ให้ clear request ทั้งหมดในช่วง 00:00:00 - 00:59:30 ออกไป แล้วก็จดเวลานี้เอาไว้ และด้วยความที่ว่าจำนวน Request ที่จดไว้มี 2 ตัว ยังไม่เกิน 2 ก็อนุญาตให้ Request B ผ่านไปได้
3. ในเวลา 1:00:50 มี Request C เข้ามา ให้ clear request ทั้งหมดในช่วง 00:00:00 - 00:59:50 ออกไป แล้วก็จดเวลานี้เอาไว้ และด้วยความที่ว่าจำนวน Request ที่จดไว้มี 3 ตัว **ซึ่งเกิน 2 แล้ว จะไม่อนุญาตให้ Request C ผ่านไปได้**
4. ในเวลา 1:01:40 มี Request D เข้ามา ให้ clear request ทั้งหมดในช่วง 00:00:00 - 01:00:40 ออกไป แล้วก็จดเวลานี้เอาไว้ และด้วยความที่ว่าจำนวน Request ที่จดไว้มี 2 ตัว ยังไม่เกิน 2 ก็อนุญาตให้ Request D ผ่านไปได้
#### ข้อดี
-  Rate Limit จะทำงานได้อย่างยุติธรรม แม้ว่าจะเป็นช่วงขอบของเวลาก็ตาม (1:00:59 ส่ง Request มาเยอะมาก ละก็ 1:01:01 ที่เป็นคนละ Window กันก็ดันส่ง Request มาเยอะมากอีกเช่นกัน ทำให้การใช้งานตรงนี้มันเหมือนไม่โดน Rate Limit)
#### ข้อเสีย
- ใช้ Memory เยอะ เพราะต้องจดเวลาอย่างสม่ำเสมอ รวมถึงเวลาของ Request ที่ไม่ผ่านด้วย

---

นอกเหนือจากนี้ มันก็ต้องมี Counter ไว้คอยนับว่าในช่วงเวลานี้ User นี้ส่ง Request มาแล้วกี่ครั้ง เพื่อเช็คว่าถึง Limit ที่กำหนดแล้วรึยัง รวมถึงก็ต้องมีค่า Timeout สำหรับแต่ละ User ด้วยอ่ะเนอะ ว่าแต่ละ User จะ reset Counter เมื่อไหร่

แล้วเราจะเก็บค่า Counter ละก็ Timeout นี้ไว้ไหนอ่ะ Database แบบเป็น Disk ก็คงไม่ดีเพราะว่ามันช้าไปสำหรับงานนี้ เลยควรเป็น In-Memory Cache ที่อ่าน-แก้ไขค่าได้รวดเร็วแหละนะ เช่น Redis อ่ะ

## 3. เจาะลึกจุดสำคัญๆ

ใดๆ ก็คือ ตอนนี้เรายังไม่ได้ระบุเลยว่า เราจะสร้าง Rate Limiter ยังไง ตอนนี้เหมือนเราแค่เตรียม Material สำหรับการสร้าง Rate Limiter เฉยๆ อ่ะ แบบว่า... Rate Limiter จะอยู่ตรงไหนดี, ใช้ Algorithm อะไรดี ...
#### 1. กำหนดว่าแต่ละ Service จะมี Rate Limit ยังไง

Rate Limiter จะมีการกำหนด Config แยก Service กันได้ เช่น

```ts
domain: messaging
descriptors:
	key: message_type
	value: marketing
	rate_limit:
		unit: day
		requests_per_unit: 5
```

อันนี้คือ มีการจำกัดว่า User 1 คนจะส่ง Message เกี่ยวกับ Marketing ได้ไม่เกิน 5 Request ต่อวัน

```ts
domain: auth
descriptors:
	key: auth_type
	value: login
	rate_limit:
		unit: min
		requests_per_unit: 5
```

อันนี้คือ มีการจำกัดว่า User 1 คนจะ Login เข้าสู่ระบบได้ไม่เกิน 5 ครั้งต่อนาที

#### 2. กำหนดว่าหากเกิน Limit จะทำยังไง

หาก User มีการใช้งาน Service ถึง Limit ที่กำหนด ก็จะมีการส่ง Response ที่มี HTTP Status 429 (Too Many Requests) ส่งกลับไปให้ Users พร้อม Header ที่เกี่ยวกับสำหรับ Rate Limiter ดังต่อไปนี้

1. X-Ratelimit-Remaining: จำนวนครั้งที่ยังสามารถส่ง Request ได้ในช่วงเวลานี้ เกี่ยวกับ Service นี้
2. X-Ratelimit-Limit: จำนวนครั้งทั้งหมดที่สามารถส่ง Request ได้ในช่วงเวลานี้ เกี่ยวกับ Service นี้
3. X-Ratelimit-Retry-After: จำนวนวินาทีที่ต้องรอ เพื่อให้สามารถส่ง Request ได้โดยไม่ติด Status 429 เกี่ยวกับ Service นี้

จาก 2 ข้อนี้ก็จะได้หน้าตา Diagram ประมาณนี้
![[design_detail_rate_limiter.png]]

ภาพการทำงานคือ...เวลา User ส่ง Request มา ก็จะชนกับ Rate Limiter ก่อน ซึ่ง Rate Limiter ตัวนี้ก็จะนำ Request ไปเช็คกฎต่างๆ ว่าต้องเอากฎข้อใดบ้างมาใช้ จากนั้นดึงค่า Counter กับ Timeout ที่เกี่ยวข้องกับ Service นั้นๆ จาก Redis มา แล้วตัดสินว่า Request นั้นจะผ่านไปได้มั้ย
- ถ้าผ่านได้ก็ปกติไป ให้ update ค่าใหม่เข้าไปใน Redis
- ถ้าผ่านไม่ได้ก็ส่ง HTTP Status 429 กลับไปให้ Users จากนั้น ระบบสามารถเลือกทำได้ 2 อย่าง คือ ทิ้ง Request นั้นไปเลย กับเก็บไว้ใน Message Queue เพื่อรอเวลาที่เหมาะสมที่จะให้ Request นั้นสามารถทำงานได้

#### 3. จะรับมือกับ Case Distributed System ยังไง

ถ้ามี Server ตัวเดียวที่จัดการระบบของเราก็ไม่มีปัญหาอะไร แต่ว่าถ้ามี Server หลายตัวที่จัดการระบบของเราขึ้นมา มันจะมีความยากที่เพิ่มขึ้นมา อย่าง Race Condition กับ Synchronization Issues
##### Race Condition
ในระบบที่มีความซับซ้อน จะแบ่ง Request ออกเป็นส่วนๆ แล้วมีการทำงานกันแบบ **Concurrent** (การทำงานพร้อมๆ กันในช่วงเวลาเดียวกัน) กันบนหลาย Server ทำให้อาจจะมีโอกาสที่บาง Server อ่านค่า Counter ตัวเดียวกันไปพร้อมๆ กัน ก่อนที่อีกฝั่งจะ Update ค่ากลับเข้าไปทัน

> [!Note] Concurrent VS Parallel 
> ![[concurrent_vs_parallel.png]] 
> - Concurrent คือการที่หลาย Task "ดูเหมือน" ทำงานพร้อมกัน แต่จริงๆ อาจจะสลับกันทำทีละนิดบน Resource เดียวกัน (เช่น CPU Core เดียว) 
> - Parallel คือการที่หลาย Task ทำงาน**พร้อมกันจริงๆ** บน Resource ที่แยกกัน (เช่นคนละ Core)

ลองดูตัวอย่างนี้: สมมติค่า Counter ใน Redis ตอนนี้คือ **3**
- Request 1 อ่านค่า Counter ได้ 3
- Request 2 อ่านค่า Counter ได้ 3 (อ่านพร้อมกันเลย ก่อนที่ Request 1 จะ Update)
- Request 1 คำนวณว่า 3+1 = 4 ไม่เกิน Limit ผ่านได้ แล้ว Update Counter เป็น 4
- Request 2 คำนวณว่า 3+1 = 4 ไม่เกิน Limit ผ่านได้เหมือนกัน แล้ว Update Counter เป็น 4 (ทับค่า 4 เดิมจาก Request 1 ไป)

ผลลัพธ์คือ Counter จบที่ **4** ทั้งที่จริงๆ แล้วมี Request เข้ามา 2 ครั้ง ค่าที่ควรจะเป็นคือ **5** ซึ่งเกิดจากการ Read-Write ที่ไม่ได้เป็น **Atomic Operation** (การกระทำที่รับประกันว่าจะทำจบในทีเดียวโดยไม่มีใครมาแทรกกลางคันได้)

##### Synchronization Issue
เพื่อรองรับ User หลักล้านคน การใช้ Rate Limiter ตัวเดียวอาจจะไม่พอ ต้องมี Rate Limiter หลายตัวมาช่วยกันรับ Traffic แต่ปัญหาคือ...เพราะ Web ของเราเป็น Stateless Client แต่ละคนเลยมีโอกาสถูกส่งไปหา Rate Limiter คนละตัวในแต่ละครั้งที่ส่ง Request พอขาดการ sync ข้อมูลกันระหว่าง Rate Limiter ก็อาจจะทำให้ User ใช้ Quota เกิน Limit ได้อ่ะนะ

![[problem_synchronization.png]]

วิธีที่สามารถทำได้เพื่อแก้ปัญหานี้ คือการใช้ คือใช้ **Redis** มาเป็น Data Store ให้ Rate Limiter ทุกตัว แทนที่แต่ละ Rate Limiter จะเก็บ Counter ของตัวเองแยกกัน
