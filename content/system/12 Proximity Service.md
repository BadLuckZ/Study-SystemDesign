## 1. ถามรายละเอียดของ Scope งาน

Q1: User สามารถกำหนดเองได้มั้ยว่าอยากหาในรัศมีกี่เมตรรอบตัว ละถ้าไม่มีสถานที่ที่ User เลือกหา ระบบจะต่อระยะรัศมีเองได้มั้ย หรือบอกไปว่าไม่มี หรือแบบไหนดี?
A1: เรา assume ว่าจะกี่เมตรก็มีสถานที่ให้แน่ๆ ก่อนละกัน

Q2: แล้วจะมี Limit ของรัศมีมั้ยครับ?
A2: เอาซัก 20 km ละกันๆ

Q3: แล้ว...ถึงจะบอกว่ากี่เมตรก็หาสถานที่ได้ บนหน้า UI จะเลือกได้มั้ยว่าอยากหาที่รัศมีกี่เมตร
A3: ก็ควรนะ เช่น 0.5km, 1km, 2km, 5km, 20km ไรงี้

Q4: แล้วพวกข้อมูลสถานที่อ่ะ เวลาที่ข้อมูลใดๆ ของสถานที่มีการเพิ่มเข้ามา หรือถูกแก้ไขไป หรือว่าถูกลบออกไป มันควรจะเห็นการเปลี่ยนแปลงแบบ Real Time เลยมั้ย
A4: เจ้าของสถานที่ก็สามารถเพิ่ม แก้ไข ลบข้อมูลสถานที่ได้เองเลย ละก็...ถือซะว่ามันจะใช้งานได้จริงในวันถัดไปละกัน

Q5: มันก็เป็นไปได้ว่า User จะเคลื่อนที่อยู่ในระหว่างใช้งาน ทำให้ result ของสถานที่ที่ได้มันจะเปลี่ยนไปจากเดิม อยากรู้ว่าเราต้อง refresh page ให้มั้ยเพื่อให้ข้อมูล up-to-date
A5: สมมติว่าไม่ต้องละกัน

### Functional Requirement

1. ระบบคืนสถานที่ตามตำแหน่งของ User และรัศมีการค้นหา
2. ผู้ประกอบการสามารถเพิ่ม แก้ไข ละก็ลบสถานที่ของตัวเองได้ แต่ว่าข้อมูลจะไม่ได้อัพเดทให้ User เห็นแบบ Real Time
3. User สามารถเห็นข้อมูลของสถานที่ได้

### Non-Functional Requirement

1. Latency ต่ำ - User ควรจะเห็นข้อมูลสถานที่ได้รวดเร็ว
2. High Availability and Scalability - ระบบต้อง handle ช่วงเวลาที่มี User ใช้งานเยอะๆ ได้ เช่นในพื้นที่ที่มี User อยู่กันเยอะๆ

### Algorithm สำหรับเลือกสถานที่

ตรงนี้น่าจะเป็นประเด็นที่ใหญ่ที่สุดของระบบละ ว่าเราจะเลือกสถานที่ที่อยู่รอบๆ User ได้ยังไง มาดูกัน

#### 1. Two-Dimensional Search

ตรงตัวเลยคือหาว่ามีสถานที่ไหนบ้างที่มี lat, lng อยู่ในช่วงรัศมี วัดจากตำแหน่งปัจจุบันของ User อาจจะพูดแล้วงง Query น่าจะชัดขึ้น

```sql
SELECT *
FROM business
WHERE (lat BETWEEN user_lat - RADIUS AND user_lat + RADIUS)
AND (lng BETWEEN user_lng - RADIUS AND user_lng + RADIUS)
```

แต่ข้อเสียเลยคือมันต้อง scan หาทั้งตาราง บางจุดที่มันเห็นทนโท่ว่าไม่อยู่ใน Area ก็ต้องเช็คด้วย ซึ่งมันไม่จำเป็น ถึงต่อให้จะทำ Index ของ lat, lmg ก็ไม่ช่วยขนาดนั้นเพราะมันคือ O(n^2) เลยอ่ะ

การจะ improve ประสิทธิภาพได้ คือเราต้องลดจาก O(n^2) ลงมาเป็น O(n) หรือเร็วกว่านั้นอ่ะ ซึ่งที่นิยมกว่าก็จะเป็น 2 วิธีด้านล่าง

#### 2. Geohash

Geohash คือการแปลงพิกัด lat, lng (2 มิติ) ให้เหลือเป็น string 1 มิติ โดยการหั่นโลกเป็น grid ซ้ำๆ ไปเรื่อยๆ (recursive) แล้วเข้ารหัสเป็น base32 เช่น 10 01 1001

![[proximity_service_geohash_overview.png]]

หลักการคือแบ่งโลกเป็น 4 quadrant ก่อน โดยใช้เส้นศูนย์สูตรกับ prime meridian เป็นตัวแบ่ง (ค่าบวกแทนด้วย 1 ค่าลบแทนด้วย 0 → ซ้ายบนคือ 01, ขวาบนคือ 11, ขวาล่างคือ 10, ซ้ายล่างคือ 00) 

จากนั้นก็แบ่งซ้ำแบบเดิมในแต่ละ quadrant ย่อยไปเรื่อยๆ จนกว่าจะเจอตำแหน่งที่ต้องการ ทุกครั้งที่แบ่งจะได้ bit เพิ่มมา 2 bit (1 สำหรับ lat, 1 สำหรับ lng) พอนำ bit ทั้งหมดที่ได้มาต่อกันแล้วแปลงเป็นเลขฐาน 32 ก็จะได้ string ประจำตัวของตำแหน่งนั้นๆ 

เช่น สำนักงานใหญ่ของ Facebook ที่มี binary `01001 10110 01001 10001 10000 10111` เมื่อแปลงเป็นฐาน 32 จะได้ `9q9jhr`

การแบ่งละเอียดแบบนี้ ยิ่ง string ที่ยาว (ระดับเยอะ) จะหมายถึง Area ที่ยิ่งเล็กลง จากระดับ 1 ที่มีขนาด 5000km x 5000km จนถึงระดับ 12 ที่มีขนาดเพียง 4cm x 2cm
**แล้วระบบควรจะเลือกความยาวของ hash ยังไง** ต้องหา length ที่ grid ครอบคลุมรัศมีที่ user เลือก คือ...
- รัศมี 5-20km ต้องทำให้ hash มีความยาว 4 
- รัศมี 1-2km ต้องทำให้ hash มีความยาว 5 
- รัศมี 0.5km ต้องทำให้ hash มีความยาว 6  

เพราะงั้นใน Usecase ตรงนี้ เราก็ควรจะแปลง (lat, lng) ของทุกสถานที่ให้เป็น hash ที่มีความยาว 6 นั่นเอง เพื่อรองรับการใช้งานที่ละเอียดสุดอย่าง 0.5km

แล้วการคืนผลลัพธ์สถานที่จะเป็นยังไง...สมมติข้อมูลก่อนละกัน
![[proximity_service_mock_data.png]]

สมมติว่า User อยู่ที่ตำแหน่ง ที่พอทำเป็น hash ละได้ `w4rqpw` 
1. ถ้า User หาในระยะ 0.5km ก็จะต้องเช็คใน Database ว่ามี Row ไหนบ้างที่ขึ้นต้นด้วย `w4rqpw` แปลว่า User ก็จะได้ข้อมูลของร้าน A ไปร้านเดียว
2. ถ้า User หาในระยะ 1-2 km ก็จะต้องเช็คใน Database ว่ามี Row ไหนบ้างที่ขึ้นต้นด้วย `w4rqp` แปลว่า User ก็จะได้ข้อมูลของร้าน A, B, C, D ไป รวม 4 ร้าน

ซึ่งจะเห็นว่ามันลดเหลือ O(n) ผ่านการเช็คแค่ค่า hash แทนที่จะเป็น O(n^2) คือเช็คทั้ง lat และ lng แยกกัน

>[!Note] ถ้าสถานที่มีไม่พอจะทำยังไง?
>สามารถลดความยาวของ hash ที่จะเช็คได้ เช่น จาก `w4rqpw` ก็เหลือแค่ `w4rqp` เพื่อให้ได้จำนวนสถานที่ครบตามที่ User ต้องการจะหา

#### 3. Quadtree

Quadtree คือโครงสร้างข้อมูลอีกแบบที่ใช้แบ่งพื้นที่ 2 มิติแบบ recursive เหมือนกัน แต่ต่างจาก Geohash ตรงที่ไม่ได้หั่นตามขนาดคงที่ทุกครั้ง แต่จะหั่นไปเรื่อยๆ จนกว่าแต่ละ grid (เรียกว่า node) จะมีจำนวนสถานที่ไม่เกิน threshold ที่กำหนดไว้ เช่น ไม่เกิน 100 ที่ต่อ node 

เพราะงั้น grid ในพื้นที่หนาแน่น (เช่นในเมือง) จะถูกหั่นละเอียดกว่า ส่วน grid ในพื้นที่โล่งๆ จะมีขนาดใหญ่กว่า ต่างจาก Geohash ที่ grid ขนาดเท่ากันหมดตาม length ที่เลือก

![[proximity_service_quadtree_overview.png]]

จากภาพตรงนี้ เราเริ่มต้นจาก Area 200_000_000 เมตร ละก็ไล่ซอยลงมาเรื่อยๆ จนกว่าจะเหลือสถานที่ไม่ถึง 100 สถานที่ใน Node นั้นๆ พอเหลือไม่ถึงแล้วเราก็หยุดแบ่ง ละวาดเป็นสี่เหลี่ยมแทน

>[!Info] 
>1. Quadtree ไม่ได้เก็บใน Database แบบ Geohash แต่จะถูกสร้างขึ้นมาเก็บไว้ใน memory ของแต่ละ LBS server ตอน server start-up เพราะงั้นทุกครั้งที่ server เริ่มทำงานใหม่ ต้องเสียเวลาสร้าง tree นี้ขึ้นมาก่อนถึงจะรับ traffic ได้
>2. Quadrant ที่มีร้านหนาแน่น เช่นในเมือง จะถูกหั่นละเอียดกว่า ส่วน quadrant ที่ว่างเปล่า เช่นในชนบท ก็จะใช้ Area ใหญ่ๆ แทน ไม่จำเป็นต้องทำเป็น Area เล็กๆ -> หรือจะบอกอีกแง่นึงก็ได้ว่า เป็นการสร้าง grid 4 ทิศที่ปรับขนาดของ grid ตามความหนาแน่นได้ ทำให้ในเมืองที่มีร้านเยอะ จะค้นหาได้แม่นยำ

สมมติข้อมูลก่อนละกัน
![[proximity_service_mock_data.png]]

ถ้า threshold ตั้งไว้ที่ไม่เกิน 2 ร้าน/node ระบบจะเริ่มแบ่งพื้นที่ทั้งหมดเป็น 4 quadrant ก่อน แล้วเช็คว่า quadrant ไหนมีร้านเกิน 2 ร้าน ก็จะหั่นต่อเฉพาะ quadrant นั้นไปเรื่อยๆ จนร้าน A, B, C, D ที่อยู่ใกล้กัน (คนละมุมของ grid เดียวกันตอนใช้ Geohash) ถูกแยกไปอยู่คนละ leaf node ย่อยๆ ตามตำแหน่งจริง ส่วนร้าน E ที่อยู่ไกลออกไปก็จะอยู่คนละกิ่งของ tree ไปเลยตั้งแต่การแบ่งรอบแรกๆ ตามภาพนี้

![[proximity_service_quadtree_mock_data.png]]

สมมติ threshold ตั้งไว้ที่ไม่เกิน 2 ร้านต่อ node
- สีเทา = node ว่างหรือยังไม่เกิน limit
- สีเหลือง = node ที่เกิน limit ต้องแบ่งต่อ
- สีเขียวอมฟ้า = leaf node สุดท้ายที่มีสถานที่จริงอยู่

**การคืนผลลัพธ์:**
1. ระบบไล่จาก root node ลงไปตาม tree ตามตำแหน่งของ User จนเจอ leaf node ที่ User อยู่
2. ถ้า leaf node นั้นมีจำนวนสถานที่พอ (เช่น ครบ threshold) ก็คืนสถานที่ใน node นั้นกลับไปเลย
3. ถ้าไม่พอ ก็ไปหยิบสถานที่จาก node ข้างเคียง (neighbor) มาเพิ่ม จนกว่าจะได้จำนวนที่ต้องการ

การไล่ลง tree แบบนี้ใช้ time complexity O(log n) ซึ่งทำให้การหาร้านทำได้ละเอียดมาก ยิ่งสถานการณ์ที่มีร้านอยู่ใกล้ๆ กันเยอะ ก็ยิ่งเห็นว่าดี แต่สิ่งที่ต้องแลก คือ 
- ความซับซ้อนตอน build และ update tree เมื่อมีร้านเพิ่ม/ลบเข้ามาใหม่
- Scaling ยาก เพราะข้อมูลอยู่ใน memory ของแต่ละ server แยกกัน

## 3. เจาะลึกจุดสำคัญๆ

### 1. Scale the Database

เราสามารถ Scale Database ได้ผ่านการทำ Sharding ผ่าน Business ID เพื่อให้ข้อมูลกระจายเข้าสู่ Database ได้อย่างเท่าเทียมกัน (ถ้าใช้ Geohash มันจะติดปัญหาว่าพื้นที่ชนบทจะมีข้อมูลน้อย แต่ในเมืองข้อมูลมันเยอะ Load จะไม่เท่ากัน หรือไม่ค่อยใกล้เคียงกัน)

แต่ในเมื่อเราไม่ Sharding ตามตำแหน่งของสถานที่ มันก็ใช้เวลา query หาสถานที่นาน เพราะงั้นก็ต้องมี Index ช่วย อย่าง Geospatial Index ที่ช่วยเช็คว่า Geohash นี้มีสถานที่อะไรบ้างได้เร็วขึ้น หน้าตา Index Table ก็จะเป็นประมาณนี้

![[proximity_service_geohash_index.png]]

โดยใช้ทั้ง `geohash` และ `business_id` เป็น Compound Key

### 2. Caching

ด้วยความที่ Index Table ของเรามีหน้าตาเป็น (geohash, business_id) แล้วการใช้ทั้งสองตัวนี้เก็บไว้ใน Cache อย่าง Redis มันก็มีประสิทธิภาพ เพราะว่าข้อมูลร้านค่อนข้างนิ่ง (ไม่เปลี่ยนบ่อย) เราเลย precompute list ของ `business_id` ต่อ geohash ไว้ล่วงหน้าได้เลย แล้วเก็บข้อมูลลงใน Redis

Flow การทำงานคือ:

1. Query หา `business_id` จาก database
```sql
SELECT business_id 
FROM geohash_index 
WHERE geohash LIKE '{:geohash}%
```

2. เช็ค cache ก่อน ถ้า miss ค่อย query database แล้วเซฟผลลัพธ์กลับเข้า cache (มี TTL ด้วย เช่น 1 วัน)

ทั้งนี้มันก็อาจจะไม่ได้คุ้มค่ามากขนาดนั้น เพราะว่าส่วนใหญ่เป็น Read และข้อมูลค่อนข้างเล็ก ทำให้ความเร็วที่ได้เพิ่มมาจาก Cache ก็ไม่ได้ทำให้ Performance มันดีมากขึ้นมากขนาดนั้นอ่ะนะ... หรือต่อให้จะ Read ได้ช้า ก็เพิ่ม Server เอาก็ได้ ไรงี้
