วันนี้เราจะมาสร้าง Payment Gateway กัน คือตัวกลางในการชำระเงิน อย่าง Beam, 2C2P, Omise หรือ Stripe ที่ร้านค้าเรียกใช้เวลาอยากรับเงินจากลูกค้า

หน้าที่หลัก คือ**รับคำสั่งจ่ายเงินจากร้านค้า ส่งต่อไปให้ธนาคารหรือเครือข่ายบัตร แล้วกลับมาบอกร้านค้าว่าเงินเข้าธนาคารแล้ว หรือยังไม่เข้า โดยห้ามตัดเงินซ้ำและห้ามเงินหาย**

ใน [[15 Payment System|Payment System]] เราเป็นร้านค้าที่ส่งงานต่อให้ PSP (Payment Service Provider) ทำ แล้ว PSP ก็เป็นเหมือนกล่องดำ คราวนี้เราจะมาเป็น PSP เอง แล้วเปิดกล่องดำนั้นดูกันว่าข้างในทำอะไรบ้าง จะเป็นไง มาดูกัน...

## 1. ถามรายละเอียดของ Scope งาน

Q1: Gateway นี้ให้บริการใครบ้างเหรอครับ?
A1: ร้านค้าออนไลน์ในไทย โดยที่เค้าจะเรียก API ของเราที่เชื่อมกับธนาคาร ไม่ได้ติดต่อธนาคารเอง

Q2: ต้องรองรับช่องทางจ่ายเงินแบบไหนบ้างครับ?
A2: เอา 2 แบบก่อน คือบัตร Credit / Debit กับ QR PromptPay

Q3: บัตรต้องรองรับการกันวงเงินไว้ก่อนแล้วค่อยตัดเงินทีหลังมั้ยครับ?
A3: ต้องมี เช่น ร้านที่ต้องเช็ค Stock ก่อนส่งของ แต่ว่าพวกร้านทั่วๆ ไปก็ตัดเงินทันที

Q4: ต้องรองรับการคืนเงินมั้ยครับ?
A4: ต้องมี ทั้งคืนเต็มจำนวนและคืนบางส่วน

Q5: เราเก็บข้อมูลบัตรเองได้มั้ยครับ?
A5: ได้ เพราะเราเป็น Gateway แต่ต้องผ่านมาตรฐาน PCI DSS (Payment Card Industry Data Security Standard: มาตรฐานความปลอดภัยเกี่ยวกับบัตรชำระเงิน)

Q6: เงินเข้าบัญชีร้านค้าตอนไหน?
A6: โอนรวมให้ร้านค้าตามรอบ เช่น วันละครั้ง หลังหักค่าธรรมเนียม

Q7: ระบบใหญ่ขนาดไหนครับ?
A7: ร้านค้า 50,000 ร้าน ประมาณ 5 ล้านรายการต่อวัน และช่วงแคมเปญพิเศษๆ อย่าง 11.11 งี้ ก็อาจจะพุ่งขึ้น 10 เท่า

### Functional Requirement

- ร้านค้าสร้างรายการจ่ายเงิน (Charge) ด้วยบัตรหรือ QR PromptPay ได้
- กันวงเงินบัตรไว้ก่อน แล้วสั่งตัดเงิน (Capture) หรือยกเลิก (Void) ทีหลังได้
- คืนเงินได้ทั้งเต็มจำนวนและบางส่วน (Refund)
- แจ้งผลการจ่ายเงินให้ร้านค้าผ่าน Webhook
- โอนเงินให้ร้านค้าตามรอบ พร้อมรายงานว่าหักค่าธรรมเนียมอะไรไปบ้าง

### Non-Functional Requirement

- Correctness: ห้ามตัดเงินซ้ำ และทุกบาทต้องตามได้ว่ามาจากไหนไปไหน
- High Availability: ถ้า Gateway ล่ม ร้านค้าทุกร้านรับเงินไม่ได้ทั้งหมด
- Security: ข้อมูลบัตรต้องปลอดภัยตาม PCI DSS
- Auditability: ย้อนดูได้ทุกรายการว่าเกิดอะไรขึ้นตอนไหน

## 2. Sketch ภาพระบบคร่าวๆ

### Business Knowledge 101

ก่อนอื่น ต้องรู้ก่อนว่าเงินกับข้อมูลวิ่งผ่านใครบ้าง ซึ่งบัตรกับ QR PromptPay จะมี Flow ที่ต่างกัน

**บัตร** จะมีตัวละครหลักๆ ก็คือ...

- **Cardholder**: ลูกค้าเจ้าของบัตร
- **Issuer**: ธนาคารที่ออกบัตรให้ลูกค้า เป็นคนตัดสินว่าจะอนุมัติรายการหรือไม่
- **Merchant**: ร้านค้า ซึ่งก็คือลูกค้าของเรา
- **Acquirer**: ธนาคารฝั่งร้านค้า เป็นคนรับรายการบัตรเข้ามา แล้วโอนเงินให้ร้านค้า (หรือให้ Gateway ไปโอนต่อ)
- **Payment Gateway**: เรา รับคำสั่งจากร้านค้า แล้วส่งต่อให้ Acquirer
- **Card Network**: เช่น Visa, Mastercard, JCB เป็นคนวางกติกา และส่งรายการระหว่าง Acquirer กับ Issuer

และการจ่ายด้วยบัตรจะเกิดเป็น 3 จังหวะ ก็คือ...

1. **Authorization**: Payment Gateway จะถาม Issuer ว่าอนุมัติการจ่ายเงินนี้มั้ย ถ้าอนุมัติ Issuer จะ**กันวงเงิน**ไว้ (เงินยังไม่ย้าย) ใช้เวลาไม่กี่วินาที
2. **Clearing**: Payment Gateway จะส่งรายการที่ Capture แล้วเป็นก้อน (Batch) ผ่าน Card Network เพื่อสรุปยอดและค่าธรรมเนียม
3. **Settlement**: เงินย้ายจริงจาก Issuer ไป Acquirer แล้วค่อยถึงร้านค้า

**QR PromptPay** จะง่ายกว่า เพราะลูกค้า**โอนเงินเอง** (Push Payment) ผ่านแอปธนาคาร

- **Thai QR Payment**: มาตรฐาน QR ของไทย ซึ่งระบบ PromptPay ดำเนินการโดย National ITMX ภายใต้การกำกับของธนาคารแห่งประเทศไทย
- **Biller ID + Reference**: QR ที่ร้านค้าใช้เก็บเงินจะเป็นแบบชำระบิล (Bill Payment) ซึ่งมี Biller ID ของเรา กับ Reference ที่เราตั้งเอง พอเงินเข้า ธนาคารจะส่ง Reference นี้กลับมา เราเลยรู้ว่าเป็นเงินของรายการไหน
- **Dynamic QR**: QR ที่ใส่จำนวนเงินมาให้แล้ว และใช้ได้กับรายการเดียว ไม่ใช่ QR ที่แปะไว้หน้าร้านให้ลูกค้ากรอกเงินเอง

> [!Tip] ทำไมต้องแยกบัตรกับ QR ให้ออก?
>
> - **บัตรเป็น Pull Payment**: เราเป็นฝ่ายดึงเงินจากบัตรลูกค้า -> กันวงเงินไว้ก่อน ยกเลิกได้ และคืนเงินผ่านระบบบัตรได้
> - **QR เป็น Push Payment**: ลูกค้าเป็นฝ่ายโอนมาเอง -> ไม่มีการกันวงเงิน เงินเข้าแล้วคือเข้าเลย ถ้าจะคืนก็ต้องโอนกลับเป็นรายการใหม่

ทำให้ State ของรายการ และวิธีคืนเงินของ 2 แบบนี้ต่างกัน

### High-Level Design

![[payment_gateway_high-level_design.png]]

จากภาพ Component หลักๆ จะมี...

- **API Gateway**: ตรวจ API Key ของร้านค้า, Rate Limit และเช็ค Idempotency Key ก่อนเข้าระบบ (อ่านเพิ่มเติมได้ใน [[01 Rate Limiter|Rate Limiter]])
- **Payment Service**: หัวใจของระบบ คุมสถานะของ Charge ทุกรายการ
- **Card Vault**: เก็บเลขบัตรแบบเข้ารหัส แล้วให้ Token กลับไปใช้แทน เป็นส่วนเดียวที่เห็นเลขบัตรจริง
- **Risk Service**: ให้คะแนนความเสี่ยงก่อนส่งรายการออกไป เช่น บัตรเดียวถูกลองหลายร้านในไม่กี่นาที
- **Acquirer / Bank Connector**: ตัวแปลงคำสั่งของเราให้เป็นรูปแบบของแต่ละธนาคาร 1 ธนาคาร 1 Connector
- **Ledger Service**: บันทึกการเคลื่อนไหวของเงินทุกรายการแบบ Double-entry
- **Webhook Service**: ส่งผลให้ร้านค้า พร้อม Retry
- **Settlement Service**: งาน Batch ที่กระทบยอดกับธนาคาร และสรุปยอดโอนให้ร้านค้า
- **Message Queue**: ส่ง Event ระหว่าง Service แบบ Async (อ่านเพิ่มเติมได้ใน [[23 Distributed Message Queue|Distributed Message Queue]])

ระบบจะมี 3 Flow ที่ต่างกัน ก็คือ...

1. Card Payment Flow
2. QR PromptPay Flow
3. Settlement Flow

#### Card Payment Flow

![[payment_gateway_card_flow.png]]

1. ลูกค้ากรอกบัตรในฟอร์มของ SDK เรา ซึ่งส่งเลขบัตรตรงมาที่ Card Vault ไม่ผ่าน Server ร้านค้าเลย แล้วได้ Card Token กลับไป
2. ร้านค้าเรียก `POST /v1/charges` พร้อม Card Token และ Idempotency Key
3. Payment Service บันทึก Charge สถานะ `PENDING` แล้วให้ Risk Service ตรวจ
4. Payment Service ส่งคำขอ Authorization ผ่าน Acquirer Connector -> Acquirer -> Card Network -> Issuer
5. ถ้าบัตรต้องยืนยันตัวตนด้วย 3-D Secure ก็ตอบร้านค้ากลับไปให้พาลูกค้าไปหน้า OTP ของธนาคารก่อน (สถานะ `REQUIRES_ACTION`)
6. Issuer อนุมัติ -> Charge เป็น `AUTHORIZED`
7. ถ้าร้านค้าตั้งให้ตัดเงินทันที ก็ Capture ต่อเลย -> `CAPTURED` แล้วบันทึก Ledger
8. ส่ง Webhook `charge.succeeded` ให้ร้านค้า = เก็บเงินจากลูกค้าเรียบร้อยแล้ว

#### QR PromptPay Flow

![[payment_gateway_qr_flow.png]]

1. ร้านค้าเรียก `POST /v1/charges` แบบ `QR_PROMPTPAY`
2. Payment Service สร้าง Charge สถานะ `PENDING` แล้วสร้าง Dynamic QR ที่มี Biller ID ของเรา, จำนวนเงิน และ Reference = `chargeId` พร้อมเวลาหมดอายุ เช่น 15 นาที
3. ร้านค้าแสดง QR ให้ลูกค้า
4. ลูกค้าสแกนด้วยแอปธนาคาร แล้วกดโอน เงินวิ่งผ่านระบบ PromptPay ไปเข้าบัญชีของเราที่ธนาคารปลายทาง
5. ธนาคารส่ง Callback มาบอกว่ามีเงินเข้า พร้อม Reference และจำนวนเงิน
6. Payment Service จับคู่ Reference กับ Charge เช็คจำนวนเงินว่าตรงกัน แล้วเปลี่ยนเป็น `SUCCEEDED` และบันทึก Ledger
7. ส่ง Webhook `charge.succeeded` ให้ร้านค้า = เก็บเงินจากลูกค้าเรียบร้อยแล้ว

#### Settlement Flow

![[payment_gateway_settlement_flow.png]]

1. ในทุกๆ คืน ธนาคารส่ง Settlement File มาให้ เป็นรายการที่ธนาคารยืนยันว่าเงินย้ายจริงแล้ว
2. Settlement Service เทียบไฟล์กับ Ledger ของเรา (Reconciliation) รายการที่ไม่ตรงกันส่งให้ทีมตรวจ
3. รายการที่ตรงแล้ว ก็รวมยอดของแต่ละร้านค้า หักค่าธรรมเนียมและยอดคืนเงิน
4. สั่งโอนเงินให้ร้านค้า (Payout) และบันทึก Ledger
5. ส่งรายงานสรุปให้ร้านค้า เพื่อให้ร้านค้าไปกระทบยอดกับระบบตัวเองต่อ

### API Design

1. **POST** `/v1/tokens` แลกเลขบัตรเป็น Card Token (เรียกจาก SDK ฝั่ง Browser ด้วย Public Key)

**Request Body**

| Field        | Description                    | Type   |
| ------------ | ------------------------------ | ------ |
| pan          | เลขบัตร                        | String |
| expiryMonth  | เดือนหมดอายุ                   | Int    |
| expiryYear   | ปีหมดอายุ                      | Int    |
| securityCode | CVV (ใช้ครั้งเดียว ไม่ถูกเก็บ) | String |

**Response**

| Field | Description                        | Type   |
| ----- | ---------------------------------- | ------ |
| token | Card Token ใช้แทนเลขบัตร           | String |
| brand | Visa / Mastercard / JCB            | String |
| last4 | เลข 4 ตัวท้าย ไว้แสดงให้ลูกค้าเห็น | String |

2. **POST** `/v1/charges` สร้างรายการจ่ายเงิน (ต้องส่ง Header `Idempotency-Key`)

**Request Body**

| Field         | Description                                      | Type    |
| ------------- | ------------------------------------------------ | ------- |
| amount        | จำนวนเงินเป็นสตางค์ เช่น `10000` = 100.00 บาท    | Long    |
| currency      | `THB`                                            | String  |
| paymentMethod | `CARD_TOKEN` (พร้อม `token`) หรือ `QR_PROMPTPAY` | Object  |
| capture       | `true` ตัดเงินทันที / `false` กันวงเงินไว้ก่อน   | Boolean |
| referenceId   | เลข Order ของร้านค้า                             | String  |
| returnUrl     | หน้าที่จะพาลูกค้ากลับมา หลังทำ 3-D Secure        | String  |

**Response**

| Field          | Description                                         | Type   |
| -------------- | --------------------------------------------------- | ------ |
| chargeId       | ID ของรายการ                                        | String |
| status         | สถานะของรายการ                                      | String |
| actionRequired | `NONE` / `REDIRECT` (ไปหน้า 3-D Secure) / `SHOW_QR` | String |
| redirectUrl    | ใช้เมื่อ `actionRequired = REDIRECT`                | String |
| qrImage        | รูป QR เมื่อ `actionRequired = SHOW_QR`             | String |
| expiresAt      | เวลาหมดอายุของ QR หรือของการกันวงเงิน               | Long   |

3. **POST** `/v1/charges/{:chargeId}/capture` ตัดเงินจากวงเงินที่กันไว้ (ส่ง `amount` น้อยกว่าเดิมได้ ส่วนที่เหลือจะถูกปล่อยคืน)

4. **POST** `/v1/charges/{:chargeId}/void` ยกเลิกการกันวงเงิน

5. **POST** `/v1/charges/{:chargeId}/refunds` คืนเงิน (ต้องส่ง Header `Idempotency-Key`)

**Request Body**

| Field  | Description                                | Type   |
| ------ | ------------------------------------------ | ------ |
| amount | จำนวนที่จะคืน ไม่ใส่ = คืนเต็มที่เหลืออยู่ | Long   |
| reason | เหตุผล เช่น `REQUESTED_BY_CUSTOMER`        | String |

6. **GET** `/v1/charges/{:chargeId}` ดูสถานะล่าสุดของรายการ

> [!Question] ทำไม Token ต้องเรียกจาก Browser ตรงๆ?
> ถ้าเลขบัตรวิ่งผ่าน Server ของร้านค้า ร้านค้าก็ต้องผ่าน PCI DSS เต็มรูปแบบด้วย ซึ่งยากและแพงมาก การให้ SDK ส่งเลขบัตรตรงมาที่เรา ทำให้ร้านค้าแตะแค่ Token และภาระ PCI DSS ส่วนใหญ่มาตกที่เราแทน

### Data Models

![[payment_gateway_schema.png]]

- **merchant**: ข้อมูลร้านค้า มี API Key, Webhook URL, Webhook Secret และอัตราค่าธรรมเนียม
- **charge**: รายการจ่ายเงิน มี `status`, `amount`, `captured_amount`, `refunded_amount`, `payment_method` และ `version` ไว้ทำ Optimistic Locking
- **refund**: รายการคืนเงิน ผูกกับ `charge_id` 1 Charge คืนได้หลายครั้งจนครบยอด
- **idempotency_key**: Key ที่ร้านค้าส่งมา พร้อม Hash ของ Request และ Response ที่เคยตอบไป
- **ledger_entry**: บันทึกการเคลื่อนไหวของเงินแบบเพิ่มอย่างเดียว (Append-only)
- **webhook_event**: Event ที่ต้องส่งให้ร้านค้า พร้อมสถานะการส่งและจำนวนครั้งที่ลองแล้ว

## 3. เจาะลึกจุดที่สำคัญๆ

### 1. Payment State Machine

ถ้าปล่อยให้แต่ละ Service แก้ `status` กันเองตามใจ วันนึงก็จะเจอรายการที่ถูก Refund ทั้งที่ยังไม่เคย Capture เลยต้องกำหนดไว้ชัดๆ ว่าเปลี่ยนจากสถานะไหนไปไหนได้บ้าง

![[payment_gateway_state_machine.png]]

```txt
บัตร:

A) PENDING -> REQUIRES_ACTION (3-D Secure) -> AUTHORIZED -> CAPTURED -> PARTIALLY_REFUNDED -> REFUNDED

B) PENDING / REQUIRES_ACTION -> FAILED

C) PENDING -> UNKNOWN (ธนาคารไม่ตอบ ดูข้อ 3. Timeout Problem) -> AUTHORIZED / FAILED

D) AUTHORIZED -> VOIDED (ร้านค้ายกเลิก) / EXPIRED (ไม่ Capture ภายในเวลา)

QR PromptPay:

A) PENDING -> SUCCEEDED -> PARTIALLY_REFUNDED -> REFUNDED

B) PENDING -> EXPIRED (QR หมดอายุ)
```

ทุกครั้งที่เปลี่ยนสถานะ ก็ใช้ Conditional Update ที่เช็คสถานะเดิมก่อนจะเปลี่ยนเป็นสถานะใหม่เสมอ เช่น

```sql
UPDATE charge
SET status = 'CAPTURED',
	captured_amount = 80000,
	version = version + 1
WHERE charge_id = 'ch_123'
AND status = 'AUTHORIZED'
AND version = 7;
```

> [!Tip] Void กับ Refund ต่างกันยังไง?
>
> - **Void**: การยกเลิกตอนที่ยังเป็น Status การกันวงเงินไว้ เงินยังไม่ได้ย้ายจริงๆ -> วงเงินลูกค้ากลับมาเร็ว และไม่มีค่าธรรมเนียมการโอน
> - **Refund**: การคืนเงินที่ตัดไปแล้ว ต้องส่งรายการใหม่ไปคืน -> ลูกค้าอาจรอหลายวันกว่าเงินจะกลับเข้าบัตร

เพราะงั้นถ้ายังไม่ได้ Capture ก็ควร Void มากกว่า Refund เสมอ

### 2. Idempotency ฝั่ง Gateway

ใน [[15 Payment System|Payment System]] เราแค่ส่ง ID ไปให้ PSP กันซ้ำ ทีนี้เราเป็น PSP เอง ก็ต้องเป็นคนเก็บและเช็ค Key นั้น

สมมติร้านค้าเรียก `POST /v1/charges` แล้ว Timeout เพราะเน็ตหลุด ร้านค้าไม่รู้ว่าเราได้รับคำสั่งหรือยัง ก็เลย Retry ด้วย `Idempotency-Key` เดิม ซึ่งเราต้องรับมือได้ 4 กรณี ก็คือ...

1. **Key ใหม่**: ทำงานตามปกติ
2. **Key เดิม และทำเสร็จไปแล้ว**: ตอบ Response เดิมกลับไปเลย ไม่ตัดเงินซ้ำ
3. **Key เดิม แต่ตัวแรกยังทำงานอยู่**: ตอบ `409 Conflict` ให้ร้านค้ารอแล้วลองใหม่ทีหลัง
4. **Key เดิม แต่ Body ไม่เหมือนเดิม**: เช่น `amount` เปลี่ยน -> ตอบ Error เพราะน่าจะเป็น bug ฝั่งร้านค้าที่ใช้ Key ซ้ำผิดที่

![[payment_gateway_idempotency.png]]

```sql
CREATE TABLE idempotency_key (
  merchant_id     BIGINT,
  idem_key        VARCHAR(255),
  request_hash    CHAR(64),        -- SHA-256 ของ Request Body
  status          VARCHAR(16),     -- IN_PROGRESS / COMPLETED
  response_code   INT,
  response_body   JSONB,
  created_at      TIMESTAMP,
  PRIMARY KEY (merchant_id, idem_key)
);
```

เวลามี Request เข้ามา ก็จะมี Step ประมาณนี้

1. `INSERT` แถวใหม่สถานะ `IN_PROGRESS` ถ้าชน Primary Key ก็แปลว่า Key นี้เคยมาแล้ว -> ไปดูกรณี 2–4
2. ทำงานจริง เช่น ส่ง Authorization ไปธนาคาร
3. อัปเดตแถวเป็น `COMPLETED` พร้อมเก็บ Response ไว้

> [!Question] ถ้า Response เป็น Error ล่ะ ต้องเก็บมั้ย?
> ต้องเก็บถ้า Error เกิดหลังจากเริ่มทำงานแล้ว เพราะเราไม่รู้ว่าก่อนพังได้ส่งอะไรออกไปบ้าง Stripe เองก็เก็บ Response แรกไว้รวมถึง `500` แต่ถ้า Request ไม่ผ่านการตรวจ Input ตั้งแต่แรก ก็ไม่ต้องเก็บ ให้ร้านค้าแก้แล้วส่งใหม่ด้วย Key เดิมได้

### 3. Timeout Problem

เรื่องที่อันตรายที่สุด คือเราส่ง Authorization ไปที่ Acquirer แล้ว**ไม่ได้คำตอบกลับมา**

**ปัญหาคือ** เราไม่รู้ว่า...

- คำขอไปไม่ถึงธนาคารเลย -> ลูกค้ายังไม่โดนกันวงเงิน
- หรือธนาคารอนุมัติไปแล้ว แต่คำตอบหายระหว่างทาง -> ลูกค้าโดนกันวงเงินไปแล้ว

ถ้าเราตอบร้านค้าว่า "ล้มเหลว" แล้วลูกค้ากดจ่ายใหม่ ในกรณีหลังลูกค้าจะโดนกันวงเงิน 2 ครั้ง เลยต้องทำแบบนี้แทน

1. เปลี่ยนสถานะเป็น `UNKNOWN` ก่อน ยังไม่ตอบว่าล้มเหลว
2. ถามธนาคารซ้ำว่ารายการนี้ผลเป็นยังไง (Inquiry) โดยใช้เลขอ้างอิงที่เราส่งไปตั้งแต่แรก
3. ถ้าถามแล้วยังไม่รู้ผล ก็ส่ง **Reversal** ไปยกเลิกรายการนั้น เพื่อให้แน่ใจว่าลูกค้าจะไม่โดนกันวงเงินค้างไว้
4. พอได้ผลชัดแล้ว ค่อยเปลี่ยนสถานะ และแจ้งร้านค้าผ่าน Webhook

ส่วนรายการที่ยังค้างอยู่ก็จะไปเจอตอนกระทบยอดกับ Settlement File อีกชั้นหนึ่ง

### 4. Settlement และ Reconciliation

แนวคิด Reconciliation อ่านได้ใน [[15 Payment System#2. Reconciliation|Payment System]] แต่ฝั่ง Gateway จะต้องเช็คยอดทั้งหมด 2 ทาง ก็คือ...

1. **กับธนาคาร**: เทียบ Settlement File ของ Acquirer และ Statement ของบัญชี PromptPay กับ Ledger ของเรา
2. **กับร้านค้า**: สร้างรายงานให้ร้านค้าเอาไปเทียบกับ Order ของตัวเอง

ตอนเทียบกับธนาคาร จะเจอรายการไม่ตรงได้ 3 แบบ

- **ธนาคารมี แต่เราไม่มี**: เช่น Timeout ในข้อ 3 ที่จริงๆ ธนาคารอนุมัติไปแล้ว -> สร้างรายการให้ตรง หรือส่งคืนเงิน
- **เรามี แต่ธนาคารไม่มี**: เช่น เราบันทึกว่า Capture แล้ว แต่คำสั่งไปไม่ถึงธนาคาร -> ส่ง Capture ใหม่ หรือเปลี่ยนสถานะ
- **มีทั้งคู่ แต่ยอดไม่ตรง**: เช่น ค่าธรรมเนียมที่ธนาคารหักไม่ตรงกับที่คำนวณไว้ -> ส่งให้ทีมการเงินตรวจ

### 5. QR PromptPay Callback Problem

QR ไม่มีปัญหาเรื่องการตัดเงินซ้ำแบบบัตร เพราะลูกค้าเป็นคนโอนเอง แต่ก็มีเรื่องที่ต้องรับมือ

#### a. Callback ไม่มา

คือถ้าลูกค้าโอนแล้ว แต่ Callback จากธนาคารหายระหว่างทาง ร้านค้าก็จะเห็นรายการค้าง `PENDING` ทั้งที่เงินเข้าแล้ว -> มี Job คอยถามธนาคารเป็นระยะ (Polling) สำหรับรายการที่ยัง `PENDING` แล้วกระทบยอดกับ Statement ของบัญชีอีกรอบตอนสิ้นวัน

#### b. Callback ซ้ำ

อีกกรณีนึง คือธนาคารอาจส่ง Callback ของรายการเดียวกันมาซ้ำ -> ใช้ Conditional Update `WHERE status = 'PENDING'` ตัวที่มาทีหลังจะไม่ได้เปลี่ยนอะไร และไม่บันทึก Ledger ซ้ำ

#### c. เงินเข้าหลัง QR หมดอายุ หรือจำนวนเงินไม่ตรง

เช่น ลูกค้าเปิดแอปค้างไว้แล้วกดโอนหลังรายการหมดอายุไปแล้ว หรือโอนผิดจำนวน -> เงินเข้ามาจริงแต่ไม่มีรายการไหนรับ ห้ามเปลี่ยนรายการที่หมดอายุกลับมาเป็นสำเร็จเอง ให้บันทึกเป็นเงินที่ยังจับคู่ไม่ได้ (Unmatched) แล้วคืนเงินให้ลูกค้าตามขั้นตอนของร้านค้า

> [!Question] ทำไมคืนเงิน QR ยากกว่าบัตร?
> บัตรมีช่องทางคืนเงินในระบบบัตรอยู่แล้ว แต่ QR เป็นการโอนเข้ามาเฉยๆ จะคืนก็ต้องโอนกลับเป็นรายการใหม่ และต้องรู้บัญชีปลายทางของลูกค้าด้วย ซึ่ง Gateway หลายเจ้า เช่น Omise ก็ไม่รองรับการคืนเงิน PromptPay ผ่าน API เลย ร้านค้าต้องจัดการเอง

### 6. Security: PCI DSS, Card Vault และ 3-D Secure

#### PCI DSS Scope

**PCI DSS** คือมาตรฐานความปลอดภัยของคนที่แตะข้อมูลบัตร ยิ่งมีระบบที่เห็นเลขบัตรมากเท่าไหร่ ก็ยิ่งต้องตรวจมากเท่านั้น เพราะงั้นหลักการคือ**ให้ส่วนที่เห็นเลขบัตรเล็กที่สุด**

- **Card Vault แยกออกมาเป็นโซนของตัวเอง**: มี Network แยก คนเข้าถึงได้น้อยที่สุด และถูกตรวจละเอียดที่สุด
- **ส่วนอื่นทั้งหมดใช้แค่ Token**: Payment Service, Ledger, Webhook ไม่เคยเห็นเลขบัตรจริง เลยไม่ต้องอยู่ในโซนที่ตรวจหนักเท่า
- **ห้ามเก็บ CVV**: ใช้ส่งไปตอน Authorization ครั้งเดียวแล้วทิ้ง

#### Card Vault

1. รับเลขบัตรจาก SDK แล้วเข้ารหัสด้วย Key ที่อยู่ใน **HSM** (Hardware Security Module อุปกรณ์เก็บ Key ที่ดึง Key ออกมาไม่ได้)
2. เก็บเลขบัตรที่เข้ารหัสแล้ว แล้วสร้าง Token แบบสุ่มที่ไม่มีความสัมพันธ์กับเลขบัตร
3. ตอนจะส่ง Authorization ก็ให้ Vault ถอดรหัสแล้วส่งตรงไปที่ Acquirer Connector ที่อยู่ในโซนเดียวกัน

#### 3-D Secure

คือขั้นตอนให้ Issuer ยืนยันตัวตนเจ้าของบัตรเพิ่ม เช่น OTP หรือสแกนหน้าในแอปธนาคาร

- **Frictionless**: Issuer ดูข้อมูลอุปกรณ์และประวัติแล้วมั่นใจ ก็ผ่านไปเลยโดยลูกค้าไม่ต้องทำอะไร
- **Challenge**: Issuer ไม่มั่นใจ ก็ให้ลูกค้ากรอก OTP -> Charge จะค้างที่ `REQUIRES_ACTION` จนลูกค้ากลับมาที่ `returnUrl`

ข้อดีอีกอย่างคือ **Liability Shift** ถ้ารายการผ่าน 3-D Secure แล้วกลายเป็นรายการโกง ความรับผิดชอบจะไปอยู่ที่ Issuer แทนร้านค้า

### 7. Webhook Constraints

ใน [[15 Payment System|Payment System]] เราเป็นฝั่งรับ Webhook (พื้นฐานอ่านได้ใน [[15 Webhook|Webhook]]) ทีนี้เราเป็นฝั่งส่ง ซึ่งจะมี 4 เรื่องที่ต้องคิด ก็คือ...

1. Webhook ต้องส่งข้อมูลให้
2. ร้านค้าต้องเชื่อได้ว่าได้ Webhook มาจากเราจริง
3. ต่อให้ร้านค้าล่ม Webhook ก็ต้องส่งใหม่ให้
4. Event อาจมาไม่ตามลำดับ

#### A) Webhook ต้องส่งข้อมูลให้

ถ้าอัปเดต Charge ลง DB สำเร็จ แต่ Service ล่มก่อนส่ง Event เข้า Queue ร้านค้าจะไม่มีวันรู้ว่าจ่ายสำเร็จ เลยเขียน Event ลงตาราง `webhook_event` **ใน Transaction เดียวกับ**การอัปเดต Charge แล้วให้อีกตัวคอยอ่านตารางนี้ไปส่งทีหลัง -> ถ้า Charge เปลี่ยน Event ก็มีแน่นอน ถ้า Charge ไม่เปลี่ยน Event ก็ไม่มี

#### B) ร้านค้าต้องเชื่อได้ว่าได้ Webhook มาจากเราจริง

ทุก Webhook จะมีลายเซ็นใน Header ที่คำนวณจาก Body ด้วย Secret ที่มีแค่เรากับร้านค้ารู้

หลักการคือ ร้านค้าจะเอา Body ที่ได้มาคำนวณซ้ำด้วย Secret เดียวกัน ถ้า signature ไม่ตรงก็ทิ้ง ส่วน `timestamp` มีไว้กันคนดัก Webhook เก่าแล้วยิงซ้ำ (Replay Attack) ถ้าเวลาเก่าเกินกำหนด เช่น 5 นาที ก็ทิ้งเหมือนกัน

```txt
signature = HMAC-SHA256(webhook_secret, timestamp + "." + raw_body)
Header: X-Signature: t=1762750000,v1=5f2b...
```

#### C) ต่อให้ร้านค้าล่ม Webhook ก็ต้องส่งใหม่ให้

ถ้าร้านค้าไม่ตอบ `2xx` ก็ลองใหม่โดยเว้นระยะห่างขึ้นเรื่อยๆ เช่น 1 นาที, 5 นาที, 30 นาที, 2 ชั่วโมง... ถ้าลองครบแล้วยังไม่สำเร็จ ก็หยุดแล้วแจ้งร้านค้าให้มากดส่งใหม่เองจากหน้า Dashboard ตัวอย่างจากของจริง เช่น Beam ลองส่ง 10 ครั้ง ส่วน Stripe ลองไปเรื่อยๆ นานสุด 3 วัน

และใช้ Queue แยกตามร้านค้า ไม่งั้นร้านค้าร้านเดียวที่ล่มจะทำให้ Webhook ของร้านอื่นช้าไปด้วย

#### D) Event มาไม่ตามลำดับ

เพราะมีการ Retry เลยอาจเกิดกรณีที่ `charge.refunded` ไปถึงก่อน `charge.succeeded` -> ใส่ `eventId` กับเวลาที่เกิดไว้ในทุก Event และแนะนำให้ร้านค้าเรียก `GET /v1/charges/{:chargeId}` เพื่อดูสถานะล่าสุดจริงก่อนทำอะไรต่อ แทนที่จะเชื่อลำดับของ Webhook

### 8. Ledger แบบ Double-entry

`status` ของ Charge บอกได้แค่ว่ารายการไปถึงไหนแล้ว แต่ไม่ได้บอกว่าตอนนี้เงินอยู่ที่ไหน และเป็นเงินของใคร เลยต้องมี Ledger แยก

หลักของ **Double-entry** คือมองเงินเป็น 2 ฝั่งที่ต้องเท่ากันตลอดเวลา

- **ฝั่งซ้าย: เงินอยู่ที่ไหน** เช่น อยู่ในบัญชีธนาคารของเราแล้ว หรือธนาคารยังค้างโอนให้เราอยู่
- **ฝั่งขวา: เงินนั้นเป็นของใคร** เช่น เป็นของร้านค้าที่เราต้องโอนต่อ หรือเป็นของเราเอง (กำไร)

ทุกบาทที่อยู่ฝั่งซ้าย ต้องมีเจ้าของอยู่ฝั่งขวาเสมอ เพราะงั้นทุกครั้งที่บันทึกรายการ ต้องแก้**อย่างน้อย 2 ที่**ให้ 2 ฝั่งยังเท่ากัน ถ้าวันไหน 2 ฝั่งไม่เท่ากัน ก็แปลว่ามีเงินโผล่มาหรือหายไปจากไหนสักแห่ง

สมมติลูกค้าจ่าย 1,000 บาท เราเก็บค่าธรรมเนียมร้านค้า 3% (30 บาท) ร้านค้าจึงได้ 970 บาท ส่วนธนาคารเก็บค่าธรรมเนียมเรา 2% (20 บาท) เงินจะเปลี่ยนไปตามนี้

| ขั้น                    | ธนาคารค้างโอนให้เรา | เงินในบัญชีเรา | ‖   | ของร้านค้า | ของเรา |
| ----------------------- | ------------------- | -------------- | --- | ---------- | ------ |
| A. Capture              | +1,000              |                | ‖   | +970       | +30    |
| B. ธนาคารโอนมา (หัก 20) | −1,000              | +980           | ‖   |            | −20    |
| C. โอนให้ร้านค้า        |                     | −970           | ‖   | −970       |        |
| **ยอดคงเหลือ**          | **0**               | **10**         | ‖   | **0**      | **10** |

ลองเช็คทีละขั้น

1. **A. Capture**: เงินยังไม่ถึงมือเรา แต่ธนาคารต้องโอนให้ 1,000 บาท -> ฝั่งซ้าย +1,000 ส่วนฝั่งขวาก็ต้องบอกว่าเป็นของใคร คือของร้านค้า 970 บาท และของเรา 30 บาท -> ฝั่งขวา +1,000 เท่ากัน
2. **B. ธนาคารโอนมา**: ยอดที่ธนาคารค้างหายไป 1,000 บาท แต่เงินเข้าบัญชีเราแค่ 980 บาท เพราะโดนหักค่าธรรมเนียม -> ฝั่งซ้าย −20 ส่วนค่าธรรมเนียมนี้เราเป็นคนจ่าย ก็หักจากส่วนของเรา -> ฝั่งขวา −20 เท่ากัน
3. **C. โอนให้ร้านค้า**: เงินออกจากบัญชีเรา 970 บาท และเราก็ไม่ได้ติดเงินร้านค้าแล้ว -> ทั้ง 2 ฝั่ง −970 เท่ากัน

พอจบครบทั้ง 3 ขั้น "ธนาคารค้างโอน" กับ "ของร้านค้า" กลับมาเป็น 0 แปลว่ารายการนี้จบสมบูรณ์ ส่วนที่เหลือในบัญชี 10 บาท ก็คือกำไรของเรา (30 − 20) ถ้าวันไหนมีช่องที่ควรเป็น 0 แต่ไม่เป็น ก็แปลว่ายังมีรายการที่ค้างอยู่

> [!Question] แล้ว Debit / Credit คืออะไร?
>
> Debit / Credit เป็นแค่ชื่อเรียก Column ซ้ายกับขวาของการบันทึกบัญชี ไม่ได้แปลว่าเงินเข้าหรือเงินออก
>
> - **Debit**: ฝั่งซ้ายเพิ่ม (เช่น ธนาคารค้างโอน +1,000) หรือฝั่งขวาลด (เช่น ของร้านค้า −970)
> - **Credit**: ฝั่งขวาเพิ่ม (เช่น ของร้านค้า +970) หรือฝั่งซ้ายลด (เช่น เงินในบัญชีเรา −970)
>
> กฎ "Debit รวม = Credit รวม" ในแต่ละรายการ จึงเป็นกฎเดียวกับ "2 ฝั่งต้องเท่ากัน" ข้างบนนั่นเอง ในตาราง `ledger_entry` แต่ละแถวจะเก็บว่าเป็นบัญชีไหน และเป็น `debit` หรือ `credit` เท่าไหร่

กติกาของ Ledger

- **เพิ่มอย่างเดียว ห้ามแก้ห้ามลบ**: ถ้าบันทึกผิด ให้บันทึกรายการกลับทาง (Reverse) เพิ่มเข้าไปแทน ประวัติจะได้อยู่ครบ
- **ยอดคงเหลือคำนวณจาก Entry**: ยอดของร้านค้า = ผลรวม Entry ของบัญชีนั้น ถ้าอยากให้อ่านเร็วก็เก็บยอดสรุปแยกไว้ได้ แต่ Entry คือความจริง
- **บันทึก 1 รายการใน Transaction เดียว**: ทุกบรรทัดของรายการเดียวกันต้องลงพร้อมกัน จะลงแค่ฝั่งเดียวไม่ได้

(แนวคิดเก็บทุกการเปลี่ยนแปลงแบบเพิ่มอย่างเดียว คล้ายกับ Event Sourcing ใน [[18 Digital Wallet#Event Sourcing|Digital Wallet]])
